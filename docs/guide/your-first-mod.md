# Your first mod

## The crate

A mod is an ordinary Rust library crate that declares one dependency:

```toml
[package]
name = "copper-lanterns"
version = "0.1.0"
edition = "2024"
license = "MIT OR Apache-2.0"

[dependencies]
ravel-sdk.workspace = true
```

One dependency to *declare* — not one crate to compile. `ravel-sdk` is a facade
over several Ravel crates and pulls in what they need, so your first build
resolves and locks a good many packages and your `Cargo.lock` will say so. What
"one dependency" buys you is the boundary: `ravel-sdk` is the only name your
manifest holds and the only name your code can write, and a transitive
dependency is not nameable in Rust.

The player's generated workspace supplies `ravel-sdk` through workspace inheritance,
so the shipped manifest must not contain your development machine's SDK path.
For local development, put your mod inside a small wrapper workspace whose root
`Cargo.toml` supplies that dependency:

```toml
[workspace]
members = ["copper-lanterns"]
resolver = "3"

[workspace.dependencies]
ravel-sdk = { path = "<path to ravel>/crates/ravel-sdk" }
```

The path must point inside a complete Ravel checkout: the SDK inherits package
metadata from its root and cannot build as a copied-out directory. Keep the wrapper
outside your shipped package. See [What does not work yet](limits.md).

`ravel-sdk` is the whole of the author-facing surface. There is deliberately no
path through it to the loader, to the JVM bindings, to a Minecraft version's
data, or to `jni`, and none of those is a dependency of it, so they are not in a
mod's dependency graph either. If you find yourself wanting to name one, the
thing you want is either somewhere in `ravel-sdk` under a different name or is
not something a mod is allowed to do.

Every mod crate should carry `#![forbid(unsafe_code)]`. Ravel's own crates do,
without exception, and a mod that needs unsafe is a mod asking for a capability
the SDK has decided not to expose.

## The mod type

A mod is a type implementing `Mod`, bound to its identity by `#[declare_mod]`:

```rust
use ravel_sdk::prelude::*;

#[derive(Default)]
pub struct CopperLanterns {
    ticks: u64,
}

#[declare_mod(id = "copper_lanterns")]
impl Mod for CopperLanterns {
    fn enter(&mut self, state: LifecycleState) -> Result<(), ModError> {
        let _ = state;
        Ok(())
    }
}
```

That is the mod itself. `enter` is the one method every mod writes, because every
mod is taken through the lifecycle; `id` is generated by the attribute, so a mod
never parses or stores its own identity. Every other method on `Mod` has a
default, so you implement only the parts of the lifecycle you take part in:
`content_declaration` to declare content that the default `register` claims,
`observe` to react to the game, `configure` to read settings,
`open_saved_data` and `save_saved_data` to own world data,
`answer_service` and `use_services` to talk to other mods, and
`interception_declaration` with `intercept` to answer at a point before the game
does something.

`#[declare_mod]` also implements `Declared`, which gives you
`CopperLanterns::declared_id()` — the identity as an associated function, usable
before an instance exists. That is how you build a content key inside an
associated function.

One more line makes it a mod a player can install:

```rust
export_mod!(CopperLanterns::default());
```

Write it once, at the root of your crate. `#[declare_mod]` binds an identity to a
type; this binds your *package* to a value. Your mod ships as source and the host
is built on the player's machine, so the generated host has to write down an
expression that produces your mod, and this is where that expression lives. A
crate that exports nothing fails that build naming itself, which is a refusal
rather than a game quietly missing a mod.

If your mod cannot be built without knowing which side it is running on, bind the
side instead — a host asks the JVM before it builds its members:

```rust
export_mod!(|side| CopperLanterns::new(side));
```

## Refusing

Every method returns `Result<(), ModError>`. Refuse with `ModError::refused("…")`,
which carries only a sentence in your own words; convert another error's text
with `ModError::from_display`.

```rust
Err(ModError::refused(
    "the lantern registry name is already taken",
))
```

The host attaches your mod's id and the lifecycle phase of the hook it called,
so a refusal names only the reason.

## Testing it

A mod is a library, so test it as one: construct it, drive it, assert on what it
did. You do not need a running game and you should not wait for one. The one
thing you have to supply yourself is a `Registrar`, because the real claim table
belongs to the loader;
[`examples/minimal-mod/src/lib.rs`](../../examples/minimal-mod/src/lib.rs) has
both an accepting and a refusing stub, about ten lines each, and copying them is
the intended route.
