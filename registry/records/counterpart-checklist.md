# Counterpart authoring checklist

The order the twelve sealed packages under `mods/` were actually written in, and the order a
thirteenth is written in. The shape of the package is `records/counterpart-template.md`; this file
is the sequence, and the sequence is where the review findings came from.

Each step is a gate. A step that cannot be completed is a finding to report, not a step to skip.

## 1. The reader and the implementer are two hands

The specification is written by a reader who saw the upstream source, for an implementer who never
will. `specifications/README.md` states the rule and
`records/mods-admissibility-2026-08-29.md` states why it is the integrity property: agreement
between a reader and a reviewer of that reader's document measures nothing.

- The reader writes `specifications/m6-foundation/RVL-NNN.md` and
  `provenance/m6-foundation/RVL-NNN.json`. Nothing else.
- The implementer reads the specification and `ravel-sdk`. Not the upstream tree, not the reader's
  notes, not the provenance record's locators.
- The independent review is a third hand, and it is a later gate. A record that says the review is
  pending is honest; a record that claims one that did not happen is the failure.

Source-blindness is mechanical, not a promise: the fetched tree lives only in the public checkout's
ignored fixture tree, and an implementer who never opens that path never read it.

## 2. Read the specification twice before writing anything

The first read is for what the entry does. The second read is for the numbers: every count, every
ordering, every refusal, every format, every bound. The second read is where the section table comes
from, and it is the read that catches a section stated in one place and contradicted in another.

Write the section table of `NOTES.md` at the end of the second read, before any Rust exists. Every
row's Here cell begins with a verdict published in `checks/counterpart-verdicts.tsv`, and that file
says which of three classes the verdict counts as: exercised, declarable-only, or excluded. The
first two are the denominator; the third is outside it. Anything after the verdict is this row's own
sentence and goes after a comma or a semicolon, so "implemented, claimed at the barrier" and
"declarable only; host-blocked, recorded as pending" are both one verdict and one explanation.

`checks/verify-notes-rows.sh` enforces it. It reads every `| §…` row of every section table, refuses
a Here cell that begins with a verdict the table does not publish, refuses a verdict the table
publishes that no row carries, adds the classes up per package and holds
`records/m6-notes-row-counts.json` to the sum. That record is generated by the check's `--write`
form and never written by hand.

Round 1 of the M6-W6 review is why this is a check rather than a convention. The four verdicts this
step used to name governed 240 of the wave's 547 rows and the other 307 carried free prose, so the
denominator was one reader's interpretation, kept nowhere, and every genuinely ambiguous row had
been resolved in the direction that shrinks it. Getting the verdict right before writing code is
still cheaper than reconciling it afterwards; the difference is that getting it wrong now fails.

## 3. Structure review

For a counterpart written from here on, this review runs before implementation. Take the module
list, the public types and the section table to a reviewer before writing bodies: the third question
below is what a transliteration fails, and it fails it before a line of Rust is written, which is
the only cheap moment to catch it.

The twelve foundation entries did not have it that way. Their structure review ran on 2026-09-05,
after the counterparts were implemented: the reader had no upstream access, read the specification
first, then read the counterpart's module list and public types, and asked the same three questions
of the pair. Eight packages changed because of it and each structural noun it found was removed from
both the specification and the counterpart. Reading the finished counterpart is plausibly a stronger
instrument than reading the specification alone, and it is a more expensive one, because what it
finds is a rewrite rather than an edit to a document. `provenance/m6-foundation/RVL-NNN.json` says
which of the two timings each entry had, and `checks/counterpart-evidence.schema.json` defines
`structureReviewed` as the review having happened and been acted on rather than as a timing.

The review is on the structure alone and asks three questions:

- Does every implemented row have a module that could hold it?
- Does every declarable-only row have a stated reason that names the missing seam, rather than a
  reason that names the effort?
- Does anything in the module list exist because the original had it, rather than because the
  specification asks for it?

## 4. The identifier rules, while writing rather than after

`checks/verify-counterparts.sh` reads every file under `mods/`, source and generated alike. Five
rules, and all five are worth knowing before the first name is chosen.

- **U1** — the file carries an upstream identifier verbatim, word-bounded and case-insensitive. The
  upstream set is read out of the M5 inventory as data: mod ids, graph node ids, graph display
  names and artifact file stems, minus the words `checks/public-word-collisions.tsv` excuses by
  hand. This is the rule a transliteration trips.
- **N1** — a name that is not verbatim but becomes one under the documented normalization: fold to
  lower case, drop every character that is not a letter or a digit. A rename by convention is still
  a transliteration. It also fires on an upstream name embedded inside a longer name.
- **L1** — every name the package gives itself is published in `checks/counterpart-lexicon.txt`.
  The package directory, the directories under it and every file stem, split on the separators a
  Rust tree uses. A word that is not published is a name nobody published.
- **L2** — the lexicon may not carry an upstream identifier, verbatim or normalized. This is the
  join where the two hand-written sides can contradict each other, which is what makes either worth
  reading.
- **L3** — the lexicon may not be padded. A published name no counterpart carries is a permission
  granted ahead of the work it would excuse, and it fails.

Practical consequences:

- Adding a module means adding its file stem's words to the lexicon in the same change, and
  removing the last package that carried a word means removing it. L1 and L3 fail in opposite
  directions, so the lexicon tracks the tree exactly.
- Prose in `NOTES.md` and in doc comments is read by these rules. "Mirrors the original's colour
  type" passes; naming the original does not.
- A namespace in a recipe or tag string is a name. If the specification requires the spelling for
  save compatibility, it goes through `aliases.json` with the exact evidence line, and the
  exemption applies to the mapping's `source` only after the whole declaration validates. Otherwise
  the entry is re-scoped to what Ravel actually carries, possibly to nothing.
- Purely numeric segments are not names. A canonical id's number is a number.

The lexicon is written by hand and derived from nothing. Do not generate it from the tree; that
would make L1 and L3 unfalsifiable.

## 5. Implement, and watch for the two defects the reviews keep finding

Both have been found more than once across the wave, and both pass every check that exists, so they
are caught by reading or not at all.

**A dispatch that resolves a name and does nothing.** A match arm, a lookup or a trait method that
correctly finds the right branch and then returns `Ok(())`, `None`, or the input unchanged. It reads
as implemented, it has a test that asserts the dispatch reached the arm, and no rule ever runs. If a
section's row says implemented, something in that module has to change a value, refuse an input, or
order a sequence, and a test has to assert the change rather than the arrival.

The corollary: do not override a trait method to give it an empty body. A method left at its default
is honest; a method overridden with a body that does nothing is the same defect wearing the
implementation's clothes.

**A bound nobody enforces.** A constant named as a maximum, a documented ceiling, a stated
grow-never-reduce rule, or a "must be a multiple of" that is written down and never compared against
anything. Every bound gets a comparison and a test that supplies a value on the wrong side of it.
Saved forms and configuration are hand-edited, so a bound over either is a trust boundary and an
unbounded count there ends the process in the allocator rather than failing an assertion.

## 6. Prove every blocking fix by mutation

Reading a test proves nothing about the test. For each fix a review calls blocking, break the input
the fix reads and require a nonzero exit, then restore it. Name the mutation and the failure it
produced in `NOTES.md`'s evidence section, the way the sealed packages do:

> Three were proved by mutation rather than by reading: removing the self-heal gate, ignoring the
> direction predicate and lifting the slot ceiling each turned a passing test red, and the last one
> ended the process in the allocator rather than failing an assertion.

A mutation that leaves the suite green means the test asserts something other than the rule. Suspect
the fixture first: a fixture that satisfies the property by accident, through sort order or through
a default, is the usual cause.

`jj restore` deletes a file that is newly added rather than reverting it, so check `jj st` before
reverting a mutation in a file the working copy shows as added.

## 7. Run the four checks

They answer four different questions and none stands in for the others. Run them from inside the
public repository's devenv shell, where `cargo`, `jq` and `check-jsonschema` are on `PATH`.

```console
checks/verify-notes-rows.sh
checks/verify-counterparts.sh
checks/verify-counterpart-packages.sh
checks/verify-counterpart-build.sh
```

- **`verify-notes-rows.sh`** — the verdict vocabulary of step 2, the per-package counts derived from
  the rows rather than from a hand, and the evidence row schema run over the public summary's rows.

- **`verify-counterparts.sh`** — the identifier rules above, plus the alias declarations, plus the
  tracked fixtures that prove the rules discriminate. It refuses to pass over an empty set.
- **`verify-counterpart-packages.sh`** — recomputes every declared digest and requires every file in
  the package to be accounted for. Refresh the digests in `package.json` last, after every other
  file is final.
- **`verify-counterpart-build.sh`** — compiles, formats, lints under clippy's default set and runs
  every test. Missing tooling is a failure here, never a skip.

Each prints what it does not catch. Read those lines: they are the disclosed ceiling, and a limit
several rounds disclose and none closes is where the next defect is.

`checks/verify.sh` runs all four along with the rest of the gate. Judge it by its exit status.

## 8. Seal by path

One counterpart is one change with a conventional message that names what the entry does. Scope the
commit to the paths the work touched, so a shared working copy does not sweep up another hand's
edits.

```console
jj commit mods/rvl-NNN-counterpart specifications/m6-foundation/RVL-NNN.md \
  provenance/m6-foundation/RVL-NNN.json checks/counterpart-lexicon.txt
```

`jj describe` takes the whole working copy, so it is not the way to seal a scoped change. Revise in
place with `jj squash --into <change>` rather than appending a fixup, and refer to the work by
change id.

Never push and never open a pull request without explicit approval in the current turn. A described
local change is completion.
