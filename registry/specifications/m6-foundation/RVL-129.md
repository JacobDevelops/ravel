# RVL-129 — behaviour specification

Wave: `waves/m6-foundation.json`. Method: source-informed reimplementation.
Rights: the upstream project's own repository root carries an MIT licence file;
see `provenance/m6-foundation.json` for the pinned revision and digest.

This document specifies **what the counterpart must do**. It deliberately says
nothing about how the original arranges its code, and where a specific algorithm
is named, the reason it is required is stated with it.

Confidence markers used throughout:

- **read** — taken directly from the pinned source.
- **inferred** — deduced from what the source does, not stated by it.
- **unknown** — could not be determined; the implementer must decide or ask.

---

## 1. What this entry is

A small shared runtime library. It carries no gameplay content of its own: it
registers nothing into the world, adds no blocks, items, recipes or worldgen,
and contributes no data or asset packs beyond its own loader declaration
(**read**). Everything it provides is consumed by other mods that depend on it.

It is loaded on both sides. A subset of its behaviour is client-only and must be
absent, not merely inert, on a dedicated server (**read** — the client-side
drawing hook is attached only when the running distribution is a client).

Its observable obligations fall into seven areas, specified below:

1. per-mod content registration, including capability attachment;
2. a per-mod play-phase message channel;
3. a positional parameter encoding used by those messages;
4. a named-action dispatch bound to a player's open screen handler;
5. optional third-party integration discovery and lifecycle;
6. a transient client-side box outline queue;
7. a colour value and a recipe-search helper for machine-like block entities.

---

## 2. Per-mod content registration

### 2.1 What it registers

The library offers a registration facade that a dependent mod creates once,
naming its own namespace. Everything registered through that facade is
registered into that namespace (**read**).

It must be able to register, all deferred until the game asks for that registry
to be populated:

- **items**, by path name, with a caller-supplied construction of the item's
  properties;
- **blocks**, by path name, with a caller-supplied construction of the block's
  properties;
- **block entity types**, by path name, bound to a set of blocks named at
  registration time;
- **data component types**, by path name, in two distinct forms: persisted only,
  or persisted **and** synchronised to clients (**read**). The distinction is
  observable and load-bearing — a component registered in the first form is not
  visible on a client at all, which is how a dependent keeps server-side detail
  off the wire. A counterpart that synchronises everything changes what dependent
  mods can hide.

### 2.2 Required coupling between a block and its item

Registering a block through this facade **also** registers an item for it, under
the same path name in the same namespace, unless the caller supplies a wrapper
that produces something else (**read**). The default item is the ordinary
block-carrying item, and its default properties use the block's own description
key rather than an item-specific one, so the registered block and its item share
a translation key by default (**read**).

This is observable and load-bearing: a caller that registers a block gets two
registry entries, not one. A counterpart that registers only the block changes
what dependent mods see.

**There is no way to ask for no item.** Every registration path for a block in
the pinned source reaches the same one that registers an item, and the wrapper
argument selects what the item is, never whether there is one (**read** — checked
against all five entry paths, because a second reader believed an opt-out
existed). A counterpart may add an opt-out, but it is an addition, not parity.

### 2.3 Registration results are handles, not values

Every registration returns a handle that resolves to the registered object later.
Callers hold these handles across the whole load, and resolve them only once the
relevant registry has been populated (**read**). Resolving a handle before its
registry is populated is a programming error; the specification does not say
what the counterpart should do in that case (**unknown** — the original relies on
the game's own deferred registry behaviour, and this document does not specify
that behaviour).

### 2.4 Capability attachment

A caller may declare that some capability should be attached to every registered
thing that satisfies a caller-supplied type test. Two forms exist: one for block
entities and one for items (**read**).

When the game asks for capabilities to be registered:

- for every block entity type registered through this facade, each declared
  block-entity capability is attached **only if** that block entity type's
  declared implementation type satisfies the declaration's type test;
- for every item registered through this facade, each declared item capability is
  attached **only if** that item satisfies the declaration's type test.

Declarations that match nothing attach nothing and are not an error (**read**).
The order in which capabilities are attached is not specified and callers must
not depend on it (**inferred** — the original iterates two collections in
registration order but nothing documents that order as a guarantee).

### 2.5 Timing

The facade must attach its own listeners at construction time, so that a mod
which constructs it during its own initialisation does not have to remember to
register anything further (**read**). Constructing the facade also announces the
namespace to the integration mechanism in §6, so integrations for that mod get
their registration callback (**read**).

## 3. Per-mod message channel

### 3.1 What it provides

A dependent mod creates one channel, naming its own namespace. Every message the
mod defines is declared to that channel before the game's payload-handler
registration point, and is registered when that point is reached (**read**).

Each message declares, as observable properties:

- a unique identifier;
- a direction — either it travels to clients or it travels to the server, never
  both (**read**);
- how to write itself to a buffer and how to read itself back;
- what to do when it arrives, given the receiving player.

The channel registers each declared message with the game's networking layer on
the side named by its direction. A message declared without a factory is refused
at declaration time with an error, rather than at registration time (**read** —
the original raises an argument error when the factory is absent).

### 3.2 Sending

The channel must be able to send:

- to every connected player;
- to one named player;
- to every player within a radius of a point in a level, optionally excluding one
  player. Both a block-aligned point and a continuous point are accepted. If no
  server is running, the send is silently dropped (**read**);
- from a client to the server.

### 3.3 Handling

A received message is handled with the receiving player supplied to it. On the
client that is the local player; on the server it is the sending player
(**inferred** — the original passes whatever the game's payload context calls the
player, and this document does not specify the thread the handler runs on;
see §9).

**unknown**: whether handlers are required to run on the main game thread. The
original delegates to the platform's payload context and does not say. The
implementer must decide this explicitly, because it is the difference between a
safe and an unsafe counterpart.

## 4. Positional parameter encoding

A message may carry a list of parameters. The encoding is **positional**: values
are written in the order given and read in the same order, and nothing in the
stream names them (**read**). Reading a parameter of the wrong type at a given
position yields wrong data rather than an error, and the specification does not
require detection of that mistake.

Required observable properties:

- **Absence is preserved.** Each parameter carries a present/absent marker.
  Reading an absent parameter yields nothing for reference types, and the type's
  zero value for numeric and boolean parameters, rather than failing (**read**).
- **The supported parameter types are fixed and known**: signed integers of
  several widths, booleans, double-precision numbers, text, a structured
  key-value tag, enumerations, and any type for which a codec has been
  registered. Item stacks and fluid stacks have codecs registered from the start
  (**read**).
- **Text is length-bounded.** A text parameter longer than 1024 encoded units is
  refused (**read**). This bound is part of the contract, not an implementation
  detail: a caller can observe the refusal.
- **Enumerations travel by declaration order, not by name** (**read**). This is a
  real hazard and the counterpart must either reproduce it knowingly or replace
  it: reordering the variants of an enumeration changes the meaning of previously
  written data. If the counterpart chooses name-based encoding instead, that is a
  deliberate divergence and should be recorded as one.
- **Requesting an unknown type fails loudly** with an error naming the type, as
  does requesting a primitive numeric type through the general accessor rather
  than its own (**read**).
- A codec registered for a type that already has one is ignored rather than
  replacing it (**read**).

**The byte layout itself is not required to match the original.** It is required
to be self-consistent: what the counterpart writes, the counterpart reads back
identically, including absence and ordering. Byte-level parity would only be
required if a counterpart had to interoperate over the wire with an unported
build of the original, and nothing in the wave says it does. If that requirement
appears later, this section must be revisited, because the layout above is
specified by property and not by byte.

## 5. Named-action dispatch

One message form is general rather than mod-specific: it carries a **name** and a
parameter list and is delivered to whatever the receiving side currently has
open. **It exists in both directions and the two differ in what they consult**
(**read**):

- the server-bound form is delivered to the screen *handler* the receiving player
  currently has open;
- the client-bound form is delivered to the *screen* the client currently has
  open.

Everything else about the two is identical, including the framing and the silent
misses below. A counterpart that provides only the server-bound direction leaves
dependants unable to push an update into an open screen.

Required behaviour:

- The currently open thing on the receiving side is consulted. If it does not
  offer a named-action table, the message is discarded silently (**read**).
- The table is looked up by the carried name. If no entry exists for that name,
  the message is discarded silently (**read**).
- If an entry exists, it is invoked with the parameters, decoded lazily — the
  parameter bytes are carried unread until the entry consumes them (**read**).
- A table maps names to handlers, last registration for a name wins, and lookup
  of an absent name yields nothing (**read**).

Silence on both miss paths is deliberate in the original and is specified here as
required behaviour: an action sent to a screen the player has since closed must
not crash the server or disconnect the client.

**Security note (inferred, not read):** the name and parameters come from the
client and are used to select and drive a server-side handler. The original
performs no authorisation beyond "the player has this screen open". A counterpart
must at minimum preserve that check, and should treat every parameter as
untrusted input. This document does not specify a stronger model, but flags that
the original's model is weak.

## 6. Third-party integration discovery

The library lets a mod ship an integration that only activates when some other
named mod is present.

Observable behaviour (**read**):

- At startup, before anything else this library does, it scans every loaded mod's
  own declared metadata for integration declarations. Each declaration names the
  foreign mod it targets and the integration to load.
- For each declaration whose target mod is actually loaded, the named integration
  is instantiated. If instantiation fails for any reason, the failure is logged
  and startup continues — a broken integration must not prevent the game from
  loading (**read**).
- Each successfully instantiated integration is then called at three points: once
  during common setup, once during client setup, and once for each registration
  facade (§2) created by the mod that shipped the integration. An integration is
  never called for another mod's facade (**read**).
- Integrations whose target mod is absent are never instantiated and never called
  (**read**).

The presence test must answer correctly both before and after the loaded-mod
list is available, because the scan runs early (**read**).

**unknown**: the order in which multiple integrations run. The original preserves
discovery order; whether dependent mods rely on that is not determinable from
this source.

## 7. Transient box outline queue (client only)

A client-side facility for drawing temporary wireframe boxes in the world.

Observable behaviour (**read**):

- A caller submits a box to outline: a position, an optional facing, the level it
  belongs to, an expiry instant, a colour, and an optional predicate that decides
  whether the box may currently be drawn.
- Submissions are de-duplicated. Two submissions are the same if they name the
  same level and the same position **and** their facings are compatible, where an
  absent facing is compatible with any facing (**read**). A duplicate submission
  is dropped entirely — it does not extend or replace the existing entry's
  expiry. That is observable and must be reproduced.
- Entries expire by their instant, earliest first. On each drawing pass, entries
  whose instant has passed are removed from the front until one that has not
  passed is reached (**read**).
- On each drawing pass, every surviving entry whose level matches the level the
  viewer is in and whose predicate (if any) currently allows it is drawn as a
  wireframe box in its colour. Entries for other levels are retained but not
  drawn (**read**).
- Drawing happens once per frame, after translucent particles, and the outline is
  visible through geometry it is behind (**read** — the original selects a depth
  test that draws where the depth buffer does not already match, and a blend mode
  that makes the lines glow; whether Ravel's renderer must match that appearance
  exactly is **unknown** and should be settled before implementation).

Expiry is only driven by the drawing pass. If nothing draws — for example while
no level is loaded — nothing expires (**read**). Whether that is intended or a
latent leak is **unknown**.

## 8. Small values and helpers

### 8.1 Colour

A colour value carries four channels — opacity, red, green, blue — held as
fractions of one. It can be built from fractions, from 0–255 integers with or
without an explicit opacity (opacity defaults to fully opaque), or from a single
packed integer in opacity-red-green-blue order, most significant byte first
(**read**).

It can be read back as fractions, as 0–255 integers, or packed in three orders:
opacity-first, opacity-last, and colour-only without opacity (**read**).

Two colours are equal when their opacity-first packed forms are equal, and that
packed form is also the value's hash (**read**). Conversion from fractions to
0–255 integers truncates rather than rounds, so a colour built from fractions and
one built from integers can compare unequal even when they look the same
(**read**). The packed layout is a wire and storage format and must be
reproduced exactly; the truncation is a defect the counterpart may choose to fix,
but fixing it changes equality and must be recorded as a divergence.

### 8.2 Recipe search state for machine-like block entities

A helper that remembers which recipe a machine is currently running so the
machine does not rescan every tick.

Observable behaviour (**read**):

- It holds a current recipe, a last-known-good recipe, a *stuck* flag and a
  *dirty* flag.
- A search first re-tests the last-known-good recipe. If it still applies, it
  becomes the current recipe and the machine is not stuck. If it no longer
  applies, the last-known-good recipe is forgotten and a full search runs over
  every recipe of the machine's kind, in whatever order the recipe store yields,
  taking the first that applies.
- A successful search clears *dirty* and *stuck* and records the recipe as both
  current and last-known-good.
- A failed search behaves differently depending on *dirty*: if the inputs changed
  since the last search, the failure only clears *dirty* and leaves the previous
  current recipe in place; otherwise the machine becomes *stuck* and has no
  current recipe.
- An input change clears *stuck* and sets *dirty*.
- The machine should tick when it has a current recipe, or when it is not stuck.
- The current and last-known-good recipes are saved with the block entity, by
  recipe identity, under a single named child of the block entity's saved data,
  and each is written only if present. On load, each identity is resolved against
  the current recipe store; an identity that no longer resolves, or that fails to
  resolve for any reason, becomes absent rather than an error (**read**). This
  makes the machine survive a recipe being removed from a pack between sessions,
  which is the behaviour the round-trip test in the wave manifest exercises.
- Loading with no level available does nothing at all (**read**).

### 8.3 Ingredient-with-quantity

A pairing of a match predicate over items or over fluids with a required quantity
(**read**). Required behaviour:

- It is built from a concrete stack (taking that stack's quantity), from a
  template, or from a predicate plus an explicit quantity.
- The quantity is required to be positive when read from data; the default when
  the field is absent is one (**read**).
- Consuming against a candidate stack does nothing if the requirement is already
  satisfied, and otherwise, if the candidate matches the predicate, moves as much
  as possible from the candidate to the requirement: the candidate is reduced and
  the outstanding requirement is reduced by the same amount, with the smaller of
  the two exhausted (**read**). This mutates the candidate in place.
- A copy is obtainable that shares the predicate but has its own outstanding
  quantity, so a requirement can be consumed without disturbing the original
  (**read**).
- It reports whether the requirement is satisfied.
- Building from a stack that carries no attached data uses a plain item-identity
  predicate; building from a stack that does carry attached data uses a predicate
  that also requires that data, with a strict rather than partial comparison
  (**read**). This distinction is observable in recipe matching and must be
  reproduced.

### 8.4 Utility encoders

Encoders for a pair, a map expressed as a list of pairs with fields named `a` and
`b`, a list prefixed by a fixed-width count, and an optional prefixed by a
present/absent marker (**read**). The pair field names and the fixed-width count
are storage formats and must be reproduced if the counterpart has to read data
written by the original; if it does not, only self-consistency is required.

## 9. What this specification does not specify

- **Rendering fidelity.** §7 says a wireframe box is drawn and describes its
  visibility through geometry. It does not specify vertex order, line width in
  any unit Ravel guarantees, shader selection, or the exact appearance. If Ravel
  needs pixel parity, that is a separate decision and this document does not
  supply it.
- **Threading.** Neither the message handlers (§3) nor the outline queue (§7)
  have a specified thread model here. The original inherits one from its host
  platform. This is the single largest gap in this document and it is deliberate:
  guessing would be worse than naming it.
- **Reflection facilities.** The original ships helpers for reaching into other
  mods' private members. They are a mechanism, not a behaviour, and a Rust
  counterpart has no equivalent surface. Nothing here specifies them, and no
  dependent behaviour was found in this source that requires them (**inferred**
  — dependants outside this source may differ).
- **The registration facade's generic breadth.** §2 lists the four registry kinds
  this source registers into. Whether Ravel's counterpart should generalise
  beyond them is a design question and is not answered here.
- **Byte-level wire parity** with unported builds of the original (§4, §8.1,
  §8.4). Only self-consistency is required unless a later decision says otherwise.
- **Ordering guarantees** for capability attachment (§2.4) and integration
  callbacks (§6). Both are marked unknown above rather than invented.
- **Error text.** Where this document says a failure is loud, it specifies that a
  failure occurs and roughly what it names, never the message string.
- **Anything the original does that this reader did not reach.** The whole of the
  pinned source for this entry was read, so this gap is believed empty, but the
  belief is a reader's.

## 10. Independent second reading

This is the only one of the five entries with a second reader. A second agent
read the same pinned source without seeing this document, wrote its own
specification of the same entry, and then stood down; its document is outside
both repositories. Comparing the two is the only real contradiction available
anywhere in this wave, and it produced three findings, all folded in above:

- the two readers **agreed** on the shape of the entry, the four declarable
  kinds, the block-implies-item default, deferred registration, behaviour-keyed
  capability binding, presence-gated integrations, silent misses in named-action
  dispatch, and the indistinguishability of absent and zero arguments;
- the second reader was **right and this document was wrong by omission** on two
  points: the two forms of data component registration (§2.1) and the existence
  of a client-bound named-action message (§5). Both are now specified;
- the second reader was **wrong** on one point: it believed a caller could
  register a block without an item. §2.2 now states the opposite explicitly, with
  the check that settles it.

Two readers who never met disagreed three times on the smallest entry in the
wave. That is the measurement, and the honest reading of it is that the four
entries with only one reader are less reliable than this one.
