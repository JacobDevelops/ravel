# RVL-146 — behaviour specification

Wave: `waves/m6-foundation.json`. Method: source-informed reimplementation.
Rights: the upstream project's repository root carries an MIT licence file, read
at the source; see `provenance/m6-foundation/RVL-146.json` for the pinned
revision, the licence identity and the digest.

Confidence markers: **read**, **inferred**, **unknown**.

This entry is a foundation seed: the wave admits it with no dependency of its
own, and three pack entries load only if it does (**read**, from the wave
manifest and the graph). It is a small toolbox rather than a mod. It contributes
no block, no item, no recipe, no tag and no loot to any world, and a player never
encounters it directly. What its dependents observe is a set of facilities: a
content-registration facade, a payload channel and a pair of generic action
payloads, a recipe-search state machine with its own persistence, an
ingredient-with-amount value, a colour value, a client block-highlight overlay,
a handful of codec helpers, and a reflection kit that Ravel declines. Sections 4
to 12 are those facilities and are the load-bearing part of this document.

## 1. What this entry is

A shared library with no gameplay of its own. Its whole purpose is to be depended
on; its own description calls it nothing but a code library (**read**). The
pinned tree holds twenty-two source files across twelve packages, one thousand
six hundred and eighty-two lines in all (**read**, counted over the whole tree
twice). Three of those files sit in the client tree (**read**). Two others are
client-facing without sitting there: the client-bound payload half of §5.1
references a client-only class directly, and §12 calls one utility client-side
though it names no client class. The rest are side-agnostic or server-facing.

The tree carries three resource documents: a mod descriptor, a resource-pack
metadata document, and a one-line access-widening declaration (**read**). It
carries two binary files: a four-hundred-pixel-square image used as the
descriptor's icon, and the build wrapper archive. The image is branding
and was not opened; the wrapper archive is build tooling and is not part of the
published artifact (**read**).

It declares itself required on both sides, with the loader and the game as its
only two dependencies and no dependency on any other pack entry (**read**, from
the mod descriptor and confirmed against the plan row's count of two platform
dependencies).

The build script names the archive after the display name and stamps it with the
declared version, which together produce the pinned artifact file name exactly
(**read**). That is how this revision was confirmed to be the pinned build.

### 1.1 Ravel disposition

Ravel already owns most of what this entry exists to provide. Content

## 2. Side, lifecycle and what happens when

The entry runs on both sides and does almost nothing at load (**read**):

- Its entry point stores itself in a process-wide slot and, on a client build
  only, subscribes one listener to the world render stage for §9's overlay. That
  is the whole of its own lifecycle participation. It registers no content, no
  payload and no capability of its own.
- The singleton slot is guarded by a Java language assertion rather than a check.
  Assertions are disabled in a normal launch, so a second construction silently
  replaces the first (**read**; the consequence is **inferred**). A counterpart
  either enforces single construction or does not need one. The slot itself is
  the original's structure; the observable consequence is only what a second
  construction does, and nothing a dependent sees requires a process-wide slot to
  exist at all.
- It offers an accessor for the currently running server, which returns absent
  when there is none. The distance-limited sends of §5 are its only callers, and
  they reach it through the process-wide slot above rather than through an
  instance of their own, so an unset slot faults there instead of yielding absent
  (**read**).
- Every other facility below is constructed by a dependent, at a time the
  dependent chooses, and this entry never drives it. The registration facade of
  §4 and the channel of §5 both have to be wired to loader events by the
  dependent; neither subscribes itself (**read**). That is the single largest
  behavioural fact about this entry: it is a set of parts, not a lifecycle.

Nothing here is client-only except the overlay subscription and the client-bound
half of §5.1 (**read**). The subscription is made under a distribution test in
the entry point. The client-bound half is guarded at the point of use by a
distribution annotation rather than a side test, and its handler reaches a
client-only process singleton. The server-bound half carries no side guard of any
kind (**read**).

## 4. Content registration

A dependent builds a collection scoped to one namespace string and declares into
it (**read**):

- a block under a path name, optionally with a factory that produces the block's
  item form;
- an item under a path name;
- a block-entity type under a path name;
- a data-component type under a path name;
- a block capability, paired with a marker interface and a provider;
- an item capability, paired with a marker interface and a provider.

Asking the collection to run registers, in this fixed order: blocks, then items,
then block-entity types, then data components (**read**). Each is registered
under an identifier formed from the collection's namespace and the declared path.

The collection object itself — a thing declarations accumulate in until it is
asked to run — is the original's structure; the observable consequence is the set
of declarable kinds above and the identifier composition, and nothing else. Do
not port the shape.

**Every declared block also gets an item.** If the dependent supplied an item
factory the item comes from it; otherwise the collection registers a default
block item with default properties. There is no way to declare a block without an
item (**read**). A counterpart makes the item optional, because a block entity
with no obtainable form is ordinary and this facade cannot express it.

**Order is fixed, but nothing read here shows it has to be.** Items are
registered after blocks, and the block-item default is built from the block
instance held in the declaration list, which exists before either pass runs
(**read**). Why the passes are separate is **unknown**. The four passes and the
order between them are the original's structure; the observable consequence is
none, because a dependent sees the identifiers and not the sequence they were
claimed in. A counterpart owes the registration order the host requires, not this
split, and any order it settles on is its own choice rather than this one carried
over.

**Capability registration is a separate entry point that nothing calls.** The
collection exposes a routine that, given the loader's capability event, walks
every declared block-entity class and registers each declared block capability
whose marker interface that class implements, then walks every declared item and
registers each declared item capability whose marker interface the item's class
implements (**read**). The base collection never subscribes that routine to
anything; a dependent that forgets to wire it gets no capabilities and no
diagnostic (**read**, **inferred** as to the silence). A counterpart makes the
wiring unnecessary rather than optional.

**A process-wide two-way cache maps block-entity classes to their types.** A
helper builds a block-entity type from a class, a factory and a block, and
records both directions. Declaring a block-entity type into the collection looks
up the class from the type through that cache, and a type that was not built
through the helper is absent and the lookup throws (**read**). So the helper is
mandatory even though nothing in the facade's signature says so.

The cache is the original's structure, in both of its directions and in its
process-wide lifetime; the observable consequences are the two stated here — the
helper being mandatory, and the collision below — and nothing in this section
asks for a lookup from a class back to its path. Do not port the shape.

That cache keys classes by their fully-qualified name string rather than by class
identity (**read**). Two classes with the same name loaded by different loaders
collide and the second silently resolves to the first. Whether the pack ever
produces that condition is **unknown**; a counterpart keys by identity and the
question does not arise.

Under Ravel a counterpart declares content in data and registers through Ravel's
own registration facilities, so the observable contract to preserve is the set of
declarable kinds and the identifier composition, not this two-pass shape.

## 5. The payload channel

A dependent builds a channel scoped to one namespace string. It hands the channel
payload factories ahead of time; the channel keeps them in declaration order and
registers all of them when the loader asks for payload handlers (**read**). A
null factory is refused at declaration time with an argument error.

Each payload declares its own identifier and a direction flag. The flag alone
decides the registration direction: flagged payloads are registered as
server-to-client, unflagged ones as client-to-server (**read**). Declaration
order has no observable effect on the wire, because every payload carries its own
identifier (**inferred**).

Each payload's transport is a hand-written pair: a writer that serialises the
payload into the buffer, and a reader that constructs a fresh instance from the
same factory and fills it from the buffer (**read**). So a payload is mutable and
is constructed empty before being filled; a counterpart decodes into an immutable
value and needs no empty state.

The payload's type token is constructed fresh from the identifier on every call
(**read**). Equality is by identifier, so this is an allocation cost rather than
a behaviour (**inferred**).

Four send helpers exist (**read**): to every player; to one named player; to
every player within a radius of a point in a level, with an optional excluded
player, in two overloads taking a block position or a floating-point position;
and to the server. The radius helpers first ask for the running server through
the process-wide slot of §2, and do nothing at all when there is none; an unset
slot faults rather than yielding absent (**read**). They then hand both the
radius and the exclusion to the platform's own distributor, which performs the
distance test. This entry does
no distance arithmetic of its own.

### 5.1 Two generic action payloads

The load-bearing piece. Two payload shapes are supplied ready-made:

- a client-to-server one, whose handler looks up the named action on the
  receiving player's currently open menu;
- a server-to-client one, whose handler looks up the named action on the client's
  currently open screen.

Each carries an action name and an optional vector of arguments. A screen or menu
opts in by exposing a map from action name to a handler taking the argument
vector; a missing name is silently ignored (**read**).

The argument vector is exposed to a handler through a small accessor offering a
strict positional read that throws when out of range, a lenient one that yields
absent, and a count. Both reads cast the stored value to whatever the caller
expects, without checking (**read**).

**The wire format is behaviour, not incidental.** Two peers must derive it
identically, so a counterpart reproduces it rather than choosing its own. The
shape is (**read**):

1. the action name, as a length-prefixed string;
2. a boolean saying whether an argument vector follows;
3. when it does: a one-byte count, then, per argument, a one-byte type tag
   followed by that type's encoding.

Eight argument types are carried, each under its own one-byte tag (**read**):
absent; integer and long, each as a variable-length quantity; short, as two fixed
bytes; boolean; string, under a thousand-and-twenty-four character bound; item
stack and compound tag, each in the game's own stream form. Any other argument
type is refused at write time with an argument error naming the offending class.

Which tag number belongs to which type is compatibility-required, because two
peers must derive it identically. This document therefore states neither the
numbering nor the order it comes from; §14 records both as obtainable from the
pinned artifact. In the original the numbering is the declaration order of a
language enumeration, so reordering the declaration silently changes the wire
(**read**, **inferred** as to the hazard). A counterpart pins the numbering
explicitly as data instead.

**This is a trust boundary and it is not defended.** The client-to-server payload
is decoded from bytes an untrusted client sent, and the following are all
**read** at the decoder:

- The argument count is written as one signed byte and read back as one signed
  byte. A vector longer than a hundred and twenty-seven wraps to a negative
  length, and the reader allocates an array of that length, which fails. A
  counterpart writes a bounded variable-length count and refuses anything outside
  the bound on both sides.
- The reader indexes the tag table by the raw byte with no range check. An
  out-of-range tag raises an index error rather than the decoder's own rejection,
  and that rejection branch is therefore unreachable. A counterpart range-checks
  the tag and rejects the packet.
- Decoding completes before the handler learns who sent it or whether any handler
  exists. A hostile peer can force a hundred and twenty-seven item-stack or
  compound-tag decodes per packet at no cost to itself. A counterpart bounds the
  decoded size, not just the element count.
- The compound-tag arm stores whatever the buffer read yields, including absent,
  so a handler expecting a tag can receive nothing (**read**; the game's reader
  may yield absent).
- The handler invokes the named action with whatever arrived, and the accessor
  casts blind. A vector of the wrong arity or wrong types reaches the handler and
  fails inside it, on the server thread (**read** at the accessor, **inferred**
  at the handler, because no handler was read). A counterpart validates arity and
  types against the registered action before dispatch, which means an action
  declares its argument shape rather than just a callback.

Under Ravel a counterpart expresses this as a typed payload over a Ravel channel
with a declared schema per action. The byte format above is what it must produce
on the wire while wire compatibility is a goal, and §14 records that the exact
identifiers involved are not this entry's to fix: each dependent supplies its own.

## 6. Recipe search

A processing block drives a small state machine over one recipe type. It holds
four pieces of state: a flag saying the search is stuck, a flag saying the inputs
changed since the last search, a remembered last successful recipe, and the
current recipe (**read**).

Searching behaves as follows (all **read**):

- If a recipe is remembered and it still matches, it becomes the current recipe,
  the stuck flag clears, and the routine returns **without touching the
  changed flag**. This is the fast path and the flag's survival across it is
  deliberate enough to be worth preserving.
- Otherwise the remembered recipe is forgotten, the stuck flag clears, and a scan
  runs over every loaded recipe of the declared type in the level, first match
  wins.
- On a match: the changed flag clears, the recipe becomes both remembered and
  current, the stuck flag clears.
- On no match: if the changed flag was set, it clears and the routine returns,
  leaving the current recipe alone and leaving the block unstuck. Otherwise the
  stuck flag sets and the current recipe clears.
- An input change clears the stuck flag and sets the changed flag.
- The block should tick when a current recipe exists, or when it is not stuck.

The net effect is a one-shot grace period: the first failed search after an input
change does not park the block, the second does. A counterpart reproduces that,
because it is what keeps a machine from parking on a transient empty inventory.

**The scan is linear in the number of recipes of the type and runs on every cache
miss.** Nothing is indexed by input (**read**). That is a disclosed ceiling: a
counterpart with an input-keyed index changes only how long a miss takes, not
what any of the flags do.

**A missing level is treated as a genuine miss** (**read**). When the level
supplier yields nothing the scan yields no match, and the no-match path then sets
the stuck flag as if the recipe list had been searched and found empty. A
counterpart distinguishes "could not search" from "searched and found nothing"
and leaves the flags alone in the first case.

### 6.1 Its persistence, which does not work

The state machine writes a nested compound under a fixed key, holding up to two
string entries: the current recipe's identifier and the remembered recipe's
identifier, each present only when set (**read**).

Reading is broken, in two independent ways.

First, the load routine returns immediately when its level supplier yields
nothing, before reading anything at all (**read**). On that path neither field is
even attempted.

Second, presence is tested on the nested compound, but the value is then read
from the **outer** compound, which has no such entry (**read**). Both reads
therefore yield an empty string. An empty string is a well-formed identifier in
the default namespace with an empty path, so parsing it succeeds, the registry
lookup simply misses, and each field is assigned absent with no throwable raised
at all (**inferred**; the identifier parser is host code this document treats as
given). Every saved recipe memory is silently lost across a save and load.

The catch clauses catch every throwable, not just parse failures, so a genuine
error inside the recipe lookup would be swallowed identically (**read**). No
throwable reaches them on the path above, so narrowing the catch is worth doing
for that reason and not because it recovers the lost memory.

This is the entry's only world data, and it is the whole of what the plan row's
registry-parity and cluster-integration expectations can be about for this entry:
this entry owns no content, so any parity test is about a dependent's content
passing through these facilities. A counterpart reads from the compound it wrote,
treats an unresolvable identifier as absent without an exception, and narrows the
catch. Doing so is a behaviour change a dependent will notice, in the direction of
the machine remembering its recipe across a restart, which is plainly what the
save was for.

## 7. An ingredient with an amount

A pairing of a matcher and a count, in two flavours: one over item stacks and one
over fluid stacks (**read**). It exists because the game's own ingredient carries
no quantity.

**Declared form.** An object with a matcher field and an optional count field
defaulting to one and constrained positive (**read**). Both field spellings are
written by pack authors and by dependents' recipe files, so §14 records them as
compatibility-required.

**Wire form.** The matcher's own stream form, followed by the count as four fixed
bytes, signed (**read**).

**The two forms disagree.** The declared form refuses a count of zero or less;
the wire form accepts any thirty-two-bit value, including negatives and values
far beyond any stack size. A counterpart applies one bound in both directions.

**Consuming.** Given a candidate stack: if the outstanding count is zero or less,
nothing happens; if the matcher rejects the stack, nothing happens; otherwise the
smaller of the available amount and the outstanding count moves. The candidate
stack is reduced by the amount moved and the outstanding count falls by the same
(**read**). Two consequences:

- The candidate stack is mutated in place, and so is the value's own outstanding
  count. This is a mutable accumulator disguised as a value: a shared instance is
  corrupted by one consume, and the copy operation exists precisely so callers can
  avoid that (**read**). The copy is shallow and shares the matcher (**read**).
- The candidate is passed untyped and cast, with a separate runtime type-check
  predicate offered so a caller can ask which flavour it holds (**read**). A
  counterpart uses a sum type over the two flavours, which removes the cast, the
  predicate and the failure mode together.

A counterpart makes the value immutable and returns the moved amount and the two
new values, and keeps the min-of-available-and-outstanding rule exactly.

Emptiness is an outstanding count of zero or less (**read**). An empty constant
exists for each flavour.

## 8. Colour

Four channels held as floating-point values, nominally in the unit interval; no
constructor clamps, so a value outside it is representable (**read**).
Constructors take four floats, three floats with the alpha implied full, four
byte-ranged integers, three byte-ranged integers with the alpha implied full, and
one packed thirty-two-bit integer read alpha-red-green-blue from the high byte
down (**read**).

Three packings are produced (**read**): alpha-red-green-blue, red-green-blue-alpha
and a twenty-four-bit red-green-blue. Every packing multiplies a channel by two
hundred and fifty-five and truncates toward zero, rather than rounding. A value
built from bytes round-trips exactly; a value built from floats loses up to one
part in two hundred and fifty-five (**inferred**, arithmetic).

Equality and the hash are both defined on the alpha-red-green-blue packing, so
two colours differing by less than one part in two hundred and fifty-five compare
equal, and the hash is the packed integer itself (**read**). A counterpart that
stores colours in a hash structure needs the same rule or its lookups differ.

The declared form is a single integer in the alpha-red-green-blue packing; the
wire form is that integer as four fixed bytes (**read**). Both are
compatibility-required.

**A hazard a counterpart avoids by construction.** The three-float and
three-integer constructors differ only in argument type, so a bare literal triple
selects the integer overload and a written one means one two-hundred-and-fifty-
fifth rather than full intensity (**read** at the signatures, **inferred** as a
hazard). Ravel's counterpart gives the two forms distinct names.

## 9. Block highlights

Client only, and host-blocked at the reviewed public revision: it draws in world
space during a render stage, and Ravel publishes no such hook. What follows is
the behaviour to implement once one exists.

A process-wide set of highlight entries is paired with a queue ordered by expiry
(**read**). An entry holds a block position, an optional face, a level key, an
expiry stamp, a box, a colour, and an optional predicate consulted each frame to
decide whether to draw.

**Adding.** If an equal entry is already present, nothing happens; otherwise the
entry joins both structures. Equality is same level key and same position, with
faces compared only when both are present, so an entry with no face matches an
entry with any face. The hash covers the level key and the position only
(**read**).

**Each frame, after particles** (**read**): entries are expired from the queue
head while the head's stamp lies in the past; then every remaining entry whose
level key matches the current level and whose predicate allows is drawn as a
wireframe box with the depth test off, at a fixed line width, in a single batch.

Three defects, all **read** at the structures:

- **Expiry desynchronises the two structures.** Expiry dequeues the head, but
  removes from the set whatever entry compares *equal to* the head. Because a
  face-agnostic entry equals a face-specific one at the same position, expiry can
  remove a different entry than the one whose time came, leaving an expired entry
  drawing forever and evicting a live one. Whether the pack's dependents ever
  create both forms at one position is **unknown**. A counterpart keys entries by
  everything its equality claims to compare, or holds one structure rather than
  two.
- **Expiry only runs while drawing.** Nothing expires when the overlay is not
  rendering, and the set is never cleared when the player leaves a world, so
  entries survive into the next world until their stamp passes. The level-key
  test hides this rather than fixing it. A counterpart clears on disconnect.
- **The stamp is absolute wall-clock time.** Lifetimes are compared against the
  system clock, so a clock adjustment lengthens or shortens every pending
  highlight. A counterpart uses a monotonic clock and stores a duration.

The render layer carries a name string. It is internal to the render pipeline and
no peer or pack author writes it, so it is not compatibility-required.

## 10. Codec helpers

Small shapes a dependent composes with (**read**):

- **A pair**, declared as an object with two single-letter fields. The spellings
  are written into data by dependents, so §14 covers them.
- **A map**, declared as a list of those pairs, decoded into a caller-supplied map
  type defaulting to an unordered hash map. Encoding iterates the map, so output
  order is the map's iteration order and is not stable across runs for the
  default; decoding inserts in list order, so a repeated key keeps the last
  occurrence (**read** for both, **inferred** for the instability). A counterpart
  either sorts on encode or states that the order is unspecified, and must not
  let a parity test depend on it.
- **A list wire form** writing a four-byte size then the elements, and reading
  exactly that many with no upper bound (**read**). The read loop counts the
  declared size down, so a zero or negative size yields an empty list rather than
  a fault; only a large positive size costs anything. On a client-to-server path
  that remainder is the untrusted-input defect of §5.1: a declared size of two
  billion loops two billion times. A counterpart bounds it.
- **An optional wire form**: a boolean then, if set, the value.
- **A compound-tag wire form** whose reader demands a non-null result and throws
  otherwise (**read**).
- **A data-component type builder** pairing a persistent declared form with a
  network form.

## 11. What a counterpart declines outright

**Reflection.** The tree carries a kit that locates a method or field by trying
several candidate names in turn and makes it accessible. When it acquires a
field, rather than before any write, it strips the final modifier from a static
final field and skips a primitive final outright (**read**). The strip is
decorative: the writes below go through raw offsets that never consult the
modifier (**inferred**, from the write path). The multiple-name
search exists to survive naming differences between builds (**inferred**).
Ravel's answer to that problem is its generated-name mapping, which is a
first-class supported surface, so the need this kit serves is already met and the
kit itself is not reimplemented.

**Direct memory access.** Underneath the kit sits a helper that obtains the Java
runtime's unsupported low-level memory interface by making a private static field
accessible, then obtains the privileged method-handle lookup by reading a private
static field at a computed memory offset, and offers typed reads and writes of
arbitrary instance and static fields through raw offsets (**read**). It is marked
internal by its own author.

Ravel forbids unsafe code in every maintained crate with no exception, and this is
precisely the category the rule exists for. A counterpart implements none of it.
A dependent that needs to reach into another package's private state is a Ravel
feature request, not a package's problem.

Declining this removes nothing a dependent can observe through a declared API: the
kit has no caller inside this tree at all (**read**, checked across the whole
tree). It exists only for dependents.

## 12. Small utilities

Five odds and ends, all **read**. They are one section because the original files
them in one place, which is its structure; the observable consequence is none,
since each behaviour below stands on its own. A counterpart puts each where it
belongs and owes no grab-bag of its own. The five are:

- A clamp of a floating-point value between a floor and a ceiling.
- A test of whether a registry holds a given identifier, in two overloads. **Its
  name says invalid and its body returns true when the identifier is present.**
  Every caller reading the name rather than the body gets the opposite of what it
  wanted. The overload taking a string parses it before testing, so the routine
  named for invalidity throws on a genuinely malformed identifier instead of
  reporting it (**read**). A counterpart names the predicate for what it returns
  and reports a malformed identifier as absent rather than throwing.
- A test of whether a mod is loaded, which consults the still-loading mod list
  when the loaded list is not yet available and the loaded list otherwise. That
  fallback is what makes it usable during construction (**inferred**).
- A rotation of a point about a centre around one axis, client-side.
- A hash strategy that treats classes as equal when their fully-qualified names
  match, which is what §4's cache is keyed by.

## 14. Spellings a counterpart must obtain rather than invent

Five spellings in this document are compatibility-required, meaning a peer, a
dependent or a pack author writes them and a counterpart that changes them breaks
that writer. None is transcribed here; each is obtainable from the pinned artifact
recorded in `provenance/m6-foundation/RVL-146.json`.

1. The eight argument type tags of §5.1 and their numbering, which two peers must
   derive identically.
2. The saved compound key of §6.1 and its two entry keys, which appear in an
   existing world.
3. The two field spellings of the ingredient shape of §7, which appear in recipe
   files written by pack authors and dependents.
4. The two field spellings of the pair shape of §10, which appear in any data
   written through it.
5. The game method the access-widening declaration of §1.2 widens, which a
   counterpart needs a named accessor for.

The guarantee is softer than it looks for items 2 and 3. Their spellings are also
the ordinary nouns §6.1 and §7 use for the same things, so a reader can
reconstruct one of item 2's two entry keys and both of item 3's field spellings
from the surrounding prose. Nothing is presented as a spelling and nothing is
quoted, and rewording those sections around the nouns would cost more clarity
than the leak is worth. A counterpart still obtains all five from the pinned
artifact rather than from this document.

Two things are deliberately **not** on that list. The payload identifiers of §5
belong to each dependent, not to this entry; and the render layer name of §9 is
internal. Everything else in this document is named for what it does, and a
counterpart is free to name it however Ravel's conventions want.
