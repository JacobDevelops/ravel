# RVL-159 — behaviour specification

Wave: `waves/m6-foundation.json`. Method: source-informed reimplementation.
Rights: the upstream project's repository root carries an MIT licence file whose
copyright line names the same author as RVL-199's and RVL-103's; see
`provenance/m6-foundation/RVL-159.json` for the pinned revision and digest.

Confidence markers: **read**, **inferred**, **unknown**.

---

## 1. What this entry is

The automation half of RVL-199. It adds seven machines that perform, without a
player present, work that RVL-199 otherwise requires a player to do by hand:
growing crops, applying growth accelerant, running the crafting grid, running
both of RVL-199's multiblock altars, upgrading essences a tier at a time, and
enchanting.

It is a leaf, and it depends on RVL-199 and RVL-162 (**read**). It is the only
entry in the wave that is mostly *machine*: about 7100 lines over 71 source
files, of which the seven machine bodies are half, against only a few dozen data
files (**read**). Unlike RVL-103 there is very little catalogue here, so this
document specifies nearly all of it.

Names in this document — grower, spreader, assembler, upgrader, enchanter, and
the two altar automatons — are labels this specification assigns by function.

## 2. The machine core

All seven machines share one core, repeated per machine rather than factored
into a base class (**read**). The shared behaviour is the specification; the
repetition is not.

### 2.1 State

Each machine holds: an item inventory, a single-slot upgrade inventory taken
from RVL-199's machine-upgrade mechanism, an energy buffer, a progress counter,
a remembered upgrade tier, a running flag, and two fuel fields — the ticks left
in the item currently burning and the total that item was worth. Everything but
the remembered tier and the running flag is persisted; both of those are
recomputed on the next tick (**read**).

The running flag is also mirrored into a block state property, and the block is
only rewritten when the flag actually changes (**read**). An implementer that
writes the block state every tick produces the same visible result and a great
deal more block-update traffic.

### 2.2 Fuel

Machines burn ordinary furnace fuel into an energy buffer; nothing accepts
energy from outside (**read**).

- Buffer capacity is 80000 by default and is scaled by the installed upgrade
  tier through RVL-199's tier mechanism.
- When the buffer is not full and nothing is currently burning, one fuel item is
  consumed and its burn time **multiplied by 20** becomes both the remaining and
  the total.
- Each tick, the buffer takes `min(remaining, usage × 2, free space)` from the
  burning item. Twice the usage rate is the transfer ceiling, so a machine fills
  at most twice as fast as it drains.
- When the remaining reaches zero the total is cleared, which is what makes the
  fuel gauge empty rather than freeze.

The usage rate and the operation time both come from the machine's own base
value scaled by the installed tier, and are the machine's base value unchanged
when no tier is installed (**read**).

### 2.3 The work step

Every machine's tick has the same skeleton (**read**):

1. run the fuel step above;
2. if the installed tier changed since last tick, re-scale the buffer capacity
   and remember the new tier;
3. clear the running flag;
4. if the buffer holds at least one operation's worth of fuel, attempt work;
5. if the running flag changed, write the block state.

**Where the machines genuinely differ is step 4, and one difference matters.**
Five of the seven check that the result can be merged into the output slot
*before* consuming any fuel, so a machine with a full output slot idles at zero
cost and loses no progress. The grower does not: it consumes fuel and advances
progress first, and inserts what it can when the operation completes (§3.1).
Anything it cannot insert is discarded. This is a real behavioural difference,
not an implementation detail (**read**).

When work is not possible, a machine with any progress accumulated resets it to
zero rather than holding it (**read**). Progress is never banked across an
interruption.

### 2.4 Sided access

Inventories are exposed per face with a fixed convention (**read**): inputs
accept insertion from above, the fuel slot accepts insertion from the north face
and only of things the level considers fuel, and everything else is refused.
Extraction is allowed from output slots and from the fuel slot when what is in
it is no longer fuel — that last clause is what lets a bucket-style fuel's empty
remainder be pulled back out.

Insertion filters on input slots are per-machine and are stated below.

### 2.5 Enablement

Every machine has its own boolean configuration value, all defaulting to on,
each also published as a feature flag through RVL-162's flag mechanism (**read**).
One further flag covers the dynamic recipe generation of §4.

## 3. The seven machines

Slot layouts below are read directly and are the wire contract for saved
inventories, so they are specification rather than incidental.

### 3.1 The grower

Grows a crop from seed with no world interaction at all — nothing is planted,
no block is placed (**read**).

- Slots: three inputs (seed, soil, optional third input), one fuel slot, nine
  output slots.
- Base operation time 800 ticks, usage 20 per tick.
- Each input slot is limited to a single item.
- It has **two** progress counters. The inner one runs to `operation time ×
  the recipe's declared stage count`, and each time it fills, the outer one
  advances by one; the outer one running to the operation time completes the
  work. So a full cycle costs `operation time² × stages` ticks — a quadratic in
  the operation time, which is either intended or a defect and this document
  cannot tell which (**inferred**).
- On completion each declared result is rolled independently against its own
  chance and the successes are distributed across the output slots in order.

### 3.2 The spreader

Applies whatever growth accelerant it holds to blocks in front of it. This is
the only machine that touches the world (**read**).

- Slots: eight inputs restricted to a published item tag, one fuel slot, no
  outputs.
- Base operation time 200 ticks, usage 40 per tick, plus a **reduced cost of 10
  for a tick that finds nothing to do**.
- It is disabled while receiving a redstone signal — the only machine that is.
- It works a square area centred `range + 1` blocks in front of the block's
  facing, where the range is a base value increased by the installed tier's
  added range. It advances through that square one position per completed
  operation using a single index that wraps, so it scans the whole square in
  order rather than choosing a position at random.
- At the chosen position, if the block accepts accelerant, the held item is used
  on it through a fake player and the full cost is charged; otherwise only the
  reduced cost is charged.
- The item is consumed only if its own use reports that it did something, which
  is what lets a non-consuming accelerant work here (**inferred**).

### 3.3 The assembler and the two altar automatons

Three machines, one behaviour, differing only in which recipe type they consult
and their slot count (**read**): a 3×3 input grid plus fuel and one output for
the assembler and for each altar automaton.

- Base operation time 200 ticks, usage 20 per tick.
- The result must be mergeable into the output before any fuel is spent.
- On completion, each input is consumed by the amount the recipe requires, and
  **an input consumed exactly one at a time leaves its crafting remainder in its
  own slot** — the bucket rule, applied per slot rather than by dropping.

The altar automatons consult RVL-199's own two altar recipe types, so those
multiblocks' recipes work here unchanged and no recipe needs restating.

### 3.4 The upgrader

Walks an essence up its tier ladder, one step per operation (**read**).

- Slots: one catalyst slot, six inputs — one per tier — one fuel, one output.
- Base operation time 100 ticks.
- The player selects a target tier index; index zero means the lowest tier and
  the machine does nothing.
- Each operation consumes **four** of the current tier's essence and produces
  one of the next, writing it either into the next tier's input slot or, when
  the next step is the selected target, into the output slot.
- The catalyst is consumed per operation, leaving its crafting remainder if it
  has one.

**A defect to diverge from.** The tier ladder's "next tier" is computed modulo
the number of tiers, so the top tier's successor is the bottom tier rather than
nothing (**read**). The accessor is annotated as possibly absent and can never
actually be absent. At the pinned revision the selected-index bound keeps this
unreachable, but it is a wrap where a stop belongs. A counterpart should make
the top tier's successor genuinely absent and should not rely on a caller's
bound to keep a wrong answer out of reach. Record the divergence.

### 3.5 The enchanter

Same shape as §3.3 with one addition: the player selects an enchantment level,
the machine asks the recipe for the maximum level its inputs can support, and
work proceeds only if that maximum is at least the selection (**read**). Base
operation time 200 ticks.

## 4. Recipes

### 4.1 The one new recipe type

The grower introduces one recipe type, published as this entry's only API
surface (**read**). Its fields:

| field | required | meaning |
| --- | --- | --- |
| seeds | yes | ingredient for the seed slot |
| soil | yes | ingredient for the soil slot |
| crux | no | ingredient for the third slot |
| stages | yes | integer; the growth-stage count of §3.1 |
| results | yes | list of `{ item, chance }` |

It serialises to the network in that order, with the optional field encoded as
optional and the result list length-prefixed (**read**). It declares itself
special and not placeable, so it never appears in the recipe book, and it is
explicitly synchronised to clients on datapack sync — this recipe type must
reach the client, which most do not (**read**).

Matching requires the input count to equal the recipe's non-empty ingredient
count exactly and then tests positionally. A recipe with no third ingredient
does not match an input that supplies one (**read**).

**A defect to diverge from.** Rolling the results uses a **process-global random
source rather than the level's** (**read**), so a harvest is not reproducible
from a world seed and draws from a source shared with everything else in the
process. This is the same defect RVL-103 §8.1 records in a different entry by
the same author; a counterpart should draw from the level's own source in both.
Record the divergence.

### 4.2 Recipes generated from another entry's registry

When its flag is on — default on — this entry generates one grower recipe per
enabled crop in RVL-199's crop registry, at recipe-manager load time (**read**).
For each crop it reads the seed item, the tier's farmland block, the essence
item, the optional crux block, and the crop block's maximum age (defaulting to 7
when there is no crop block), and produces a recipe whose results are the
essence at certainty plus RVL-199's fertilised-essence item at that entry's own
configured chance.

Two properties are worth carrying (**read**):

- a crop missing any of seed, farmland, or essence is skipped rather than
  producing a broken recipe; and
- **the lowest-tier crop is excluded by name.** A string comparison against a
  fixed name is the mechanism. It is exactly the kind of exclusion that belongs
  in data, and a counterpart should express it as a property of the crop rather
  than as a name test — but the exclusion itself is behaviour and must be kept,
  or that crop gets a recipe the original does not have.

### 4.3 The ingredient cache

Input slots do not test recipes directly; they test a cache (**read**).

On recipe-manager load, the server walks every grower recipe and builds three
maps — one per input slot — from item to the list of ingredients that accept it.
A slot's insertion test looks the incoming item up in its map and asks whether
any ingredient there accepts the stack.

The cache is **rebuilt on the server and pushed whole to clients** on datapack
sync: to the joining player if there is one, otherwise to everyone (**read**).
Clients need it because the same insertion test runs client-side against the
container.

This is a performance structure with a correctness consequence: an input slot
accepts an item if *any* grower recipe would take it in that position, not only
the recipe that matches the other slots. Filling all three slots with items each
valid alone but not together is possible and simply produces no work.

## 5. The network surface

Four payloads on one versioned channel (**read**):

| payload | direction | purpose |
| --- | --- | --- |
| ingredient cache | to client | the whole of §4.3 |
| selected tier index | to server | §3.4 |
| selected enchantment level | to server | §3.5 |
| set a display-only recipe slot | to server | the ghost-recipe display |

**unknown**: what the last one validates. Not read.

---

## 6. Blocks and containers

Each machine block is a horizontally-facing block with the running property of
§2.1, opens its container on use, and drops its upgrade item when broken
(**read**). Containers expose the machine's synchronised fields — buffer amount
and capacity, fuel remaining and total, progress, operation time, and for the
grower its stage counters — through the standard indexed data mechanism.

## 7. What this specification does not specify

- **Screens, widgets, and the guidebook entries.** Roughly a third of the source
  is client presentation; its mechanisms were not read beyond confirming that
  the two selection payloads of §5 originate there.
- **The optional integrations**, including the recipe-transfer handlers and the
  scripting hook. Present, unread.
- **The display-only recipe slot's validation** (§5), marked unknown.
- **Whether the grower's quadratic cycle cost is intended** (§3.1), marked
  inferred.
- **The item and block catalogue**, the loot tables, the tag contents, and the
  hand-written recipe files. Small here compared to RVL-103, and still data.
- **Coverage.** Read in full: the machine core, all seven machines' work steps
  and slot layouts, the recipe type and its wire format, the generated-recipe
  rule, the ingredient cache, the network surface, the configuration, and one
  block. Read in part: the remaining blocks and the containers, for the shape
  §6 states. Everything else: listed, not read.
