# RVL-162 — behaviour specification

Wave: `waves/m6-foundation.json`. Method: source-informed reimplementation.
Rights: the upstream project's repository root carries an MIT licence file; see
`provenance/m6-foundation.json` for the pinned revision and digest.

Confidence markers: **read**, **inferred**, **unknown**.

---

## 1. What this entry is

A shared content-authoring library. Unlike RVL-129 and RVL-217 it does register
things into the world, but only a handful, and the bulk of what it provides is
building material for the mods that depend on it (**read**).

It runs on both sides, with a substantial client-only part that must be absent on
a dedicated server (**read**).

What it registers under its own namespace (**read**):

- one data component type: a boolean marking a watering tool as filled;
- one sound event: the watering tool's loop;
- one recipe condition kind: the feature-flag condition of §3;
- four crafting recipe kinds: §4;
- one command tree: §6;
- item and block tags naming which blocks its area tools mine and which items are
  each of its tool kinds, plus additions to several stock tool and enchantability
  tags.

It also loads a handful of behavioural patches into the game's own recipe
handling and model baking (**read**). Those are a mechanism; §8 says which
observable behaviours depend on them.

---

## 2. Startup order

At construction (**read**):

- the four registries above are attached;
- on a client only, three registration handlers are attached: item model
  properties, tint sources, and render layers;
- feature-flag declarations are discovered across every loaded mod (§3);
- two configuration files are registered, one client-side and one common.

At common setup, the command tree and the tag-mapping file handler are attached
to the game event bus. At client setup, three further handlers are attached: bow
field-of-view, tag tooltips and data-component tooltips (**read**).

The ordering matters in one place: feature-flag discovery must happen before any
data pack is parsed, because the recipe condition in §3 is evaluated during pack
loading and an undiscovered flag evaluates as disabled (**inferred** — the
original does discovery in the constructor and nothing states the requirement,
but the condition's fallback makes the consequence observable).

---

## 3. Feature flags

A **feature flag** is a named boolean, published by any mod, that data packs can
test.

Observable behaviour (**read**):

- A flag is created with an identifier and a predicate that answers whether it is
  currently enabled. Creating it publishes it under that identifier; the last
  creation for an identifier wins.
- A flag may also be *referenced* by identifier without a predicate. Such a
  reference resolves its predicate lazily, on first use, from whatever is
  published under that identifier at that moment. **An unpublished identifier
  resolves to permanently disabled**, and — this is the part a counterpart must
  reproduce — once resolved it stays resolved, so a reference used before the
  publishing mod loaded will read as disabled forever afterwards.
- Discovery: at startup the library scans every loaded mod's declared metadata
  for classes marked as flag declarations, and forces each one to load, which is
  what causes its flags to be published. A declaration that fails to load is
  logged and skipped (**read**).
- The library publishes two flags of its own, one per client tooltip setting
  (§5).

A data pack condition tests a flag by identifier: the guarded recipe, tag or
other conditioned entry exists when the flag is enabled and does not exist when
it is not (**read**).

**unknown**: whether a flag's predicate is re-evaluated on every test or cached.
The original re-evaluates the predicate each time but caches the *resolution* of
a reference; whether dependants rely on live re-evaluation is not determinable
here.

## 4. Crafting recipe kinds

Four crafting recipe kinds are registered. All four match by the stock shaped or
shapeless pattern rules — they change only what comes out (**read**).

### 4.1 Result taken from a tag

Two kinds, one shaped and one shapeless. The recipe's result is stated as a tag
identifier and a count rather than as an item. At the moment the result is
needed, the tag is resolved to a single concrete item by §7, and the result is
that item in that count (**read**).

Required behaviour:

- The result is resolved **once** and remembered for the life of the recipe
  object in the shaped form (**read**). Whether that caching is required or
  incidental is **unknown**; it is observable if the tag mapping changes at
  runtime, which §7 permits.
- The result field accepts either a plain item stack or the tag form, and the two
  are mutually exclusive (**read**).
- When the recipe is sent to a client, the **already-resolved concrete stack** is
  sent, not the tag (**read**). This is required behaviour: clients never resolve
  the tag themselves, so a server whose mapping differs from a client's still
  displays consistently.

### 4.2 Result inheriting damage

A shaped kind that copies wear from an input to the output. Behaviour (**read**):

- The first input slot, in slot order, holding a damageable item is selected.
- If none is found, the plain result is produced.
- Otherwise, if the recipe's flag says to transfer all attached data, the whole
  attached-data patch of that input is applied to the result; if it does not, only
  the damage value is copied.

The flag is a required field of the recipe, not optional (**read**).

### 4.3 Result inheriting attached data from a named slot

A shaped kind that takes a slot index as a required field and applies the
attached-data patch of whatever is in that slot to the result (**read**). No
bounds check on the index appears in this source; an out-of-range index is
**unknown** behaviour and a counterpart should make it a load-time error rather
than reproduce whatever the original does.

## 5. Tooltips

Two client-only tooltip behaviours, each gated on its own client setting and
each also published as a feature flag (**read**):

- **Tag tooltips**, on by default: shows the tags a block or item belongs to.
- **Attached-data tooltips**, off by default: shows an item's attached data.

The gating is doubled on purpose: the setting controls the tooltip, and the flag
of the same name lets data packs condition on the setting. A counterpart must
keep them consistent, because a pack can observe the flag while a player observes
the tooltip.

**unknown**: the exact rendering, ordering and modifier-key behaviour of either
tooltip. Not read in detail.

---

## 6. Command

One command tree rooted at the library's own namespace, with a single
administrative subcommand that fills something with energy (**read**):

- one form targets the block the invoking player is looking at, using the face
  they are looking at;
- one form targets the item in the player's main hand.

In both cases: if the target offers an energy store, it is filled to its capacity
in one committed transaction and a success message is sent; if it does not, or if
the hand is empty, a failure message is sent. Both messages are translated and
name which of the two forms was used (**read**). The command requires
administrator permission (**read**).

The command's outcome value is zero in every path, including failures (**read**).
That is almost certainly a defect; a counterpart should return a meaningful
value and record the divergence.

## 7. Tag-to-item mapping

This is the most side-effectful behaviour in the entry and the one most likely to
surprise. It exists so a recipe can say "some copper ingot" and get whichever mod's
copper ingot the pack prefers (**read**).

### 7.1 The file

A JSON object lives in the game's configuration directory under a name derived
from this library. It maps tag identifiers to item identifiers. It is created if
absent, containing only a single comment entry pointing at documentation
(**read**).

### 7.2 Resolving a tag

Given a tag identifier (**read**):

1. If an external unification integration is present and offers a preferred item
   for that tag, that item is used and nothing else happens.
2. Otherwise, if the in-memory mapping holds the tag, its item identifier is
   resolved against the item registry. **An identifier that resolves to nothing
   yields air**, not an error.
3. Otherwise the file is read. If it names the tag with a non-empty, non-`null`
   value, that value is remembered and resolved as above.
4. Otherwise the tag is *chosen* (§7.3), written into the file, remembered, and
   the file is saved.

A resolution that ends in air is reported as "this tag has no entries" at warning
level, and the recipe result becomes a barrier item in the requested count
(**read**). That is deliberate: the recipe stays loadable and the problem is
visible in-game rather than crashing the load.

### 7.3 Choosing an item for a tag

Among the tag's bound members, the one whose namespace appears earliest in a
configured ordered list of preferred namespaces wins. Members whose namespace is
not in the list rank between "listed" and "later-listed" under the original's
comparison, which is not a total order and therefore does not produce a
deterministic winner in every case (**read**, and stated here as a defect).

**A counterpart must not reproduce the non-determinism.** It must define a total
order — preferred namespaces in list order first, then everything else by a
stable rule such as registry order or lexicographic identifier — and record the
choice as a divergence. The observable requirement is: for a given tag, a given
namespace list and a given set of members, the same item is chosen every time,
on every machine.

If the tag has no bound members, the file records the literal string `null` for
it and resolution yields air (**read**).

### 7.4 Refreshing

A common setting, on by default, makes the library re-check every mapped entry
whenever tags are updated: any entry whose item no longer exists is re-chosen and
the file is rewritten (**read**). With the setting off, stale entries persist and
resolve to air.

The re-check runs on the tags-updated event, and only when that event says static
data should be updated (**read**).

### 7.5 What this means for the counterpart

The mapping file is **shared mutable state on disk, written during data load**.
Two observable consequences follow and both must be preserved or deliberately
changed:

- a pack ships without the file and gets one written on first load;
- an operator can pin a tag to a specific item by editing the file, and that
  choice survives unless §7.4 invalidates it.

A counterpart that resolves tags purely in memory is not equivalent.

## 8. Behaviour supplied to dependent mods

The library's largest surface is building material: base implementations of
blocks, items, tools, block entities, screen handlers, screens, widgets,
inventories and helpers. These are **not** specified individually here, for the
reason the clean-room brief gives: reproducing the original's decomposition
through prose is the failure this process exists to prevent.

What is specified is the observable behaviour dependants rely on. The following
were read and must hold:

### 8.1 Area-harvest tools

Two tool behaviours share a shape: a player-triggered action affects a cubic or
planar region around the target rather than a single block.

- **Region mining tool.** On breaking a block it can correctly mine, it also
  breaks every block within a configured radius in all three axes that it can
  also correctly mine and whose hardness does not exceed the originally broken
  block's hardness by more than five. It mines its own tagged blocks at half its
  material's speed (**read** — halved, which is unusual and deliberate). Breaking
  a zero-hardness block costs one durability with probability one third, and
  costs nothing in creative mode (**read**).
- **Crop-harvest tool.** Used against a block face, it harvests every fully grown
  crop in a flat square of a configured radius at the clicked height, replacing
  each with its zero-age state and dropping its produce, and does the same for
  one specific fully grown stock plant. Each harvest costs one durability. If
  anything was harvested, a break sound plays once at the clicked position
  (**read**).
  - Each individual harvest is announced as a cancellable event **before** it
    happens, and separately as the game's own cancellable block-break event.
    Either cancellation skips that block and nothing else (**read**). Dependent
    mods hook this; it is public behaviour, not an internal detail.
  - Used as a weapon, at 95% or more of full attack charge it also damages every
    other living entity within an inflated box around the target, for two thirds
    of its attack damage, with knockback, skipping the wielder, the target, and
    anything allied to the target; then plays the stock sweep sound (**read**).
    The box grows with the tool's radius on the horizontal axes only.

### 8.2 Events published for dependants

Four events are published and dependants listen to them (**read**):

- an item was broken (destroyed by durability loss);
- the recipe store is about to load, and has finished loading;
- a crop is about to be harvested by the crop tool (cancellable, §8.1);
- client item registration.

The two recipe-store events exist because the library needs a point at which
every recipe is known; they are the reason for one of the behavioural patches
mentioned in §1 (**inferred**).

### 8.3 Watering tool

A tool that, while held and used, keeps a looping sound playing on the client for
that player and stops it when use ends. The sound is per-player and starting it
twice for the same player does nothing (**read**). Its filled state is carried by
the data component of §1.

## 9. What this specification does not specify

- **The default preferred-namespace list** (§7.3). It is five specific third-party
  namespaces in the original. Naming them here would put upstream identifiers in
  a clean-room specification, and in any case the right list for Ravel is a pack
  policy rather than a property of this entry. The requirement specified is that
  the list exists, is ordered, is configurable, and is non-empty by default.
- **The base classes.** §8 explains why. A counterpart is expected to arrive at
  its own decomposition and be judged on the behaviours in §8, not on shape.
- **Screen and widget appearance.** Progress arrows, energy bars, fuel gauges,
  icon buttons and the container screen base were seen to exist and were not read
  in behavioural detail. Nothing here specifies them.
- **The behavioural patches** into the game's own recipe handling, model baking,
  item stacks and server resources. Their existence is recorded; what they do was
  not read. This is a real gap: at least one dependant behaviour (§8.2's
  recipe-store events) is produced by one of them, and a counterpart will need
  either the same hook points from Ravel or a different route to the same event.
- **The optional recipe-viewer integration.** Present in the source, not read,
  not specified.
- **Tooltip rendering** (§5).
- **Bounds behaviour of the slot-index recipe field** (§4.3), marked unknown.
- **Coverage.** Read in full: the entry point, all four registries, both
  configuration files, the flag mechanism and its condition, all four recipe
  kinds and the result resolver, the tag mapper, the command, and the two area
  tools. Everything else in this entry was listed but not read.
