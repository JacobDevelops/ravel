# RVL-180 — behaviour specification

Wave: `waves/m6-foundation.json`. Method: black-box respecification.
Rights: the pinned artifact carries a weak-copyleft licence and the M5 triage
records this entry's code surface as permission-required and its `sourceUse` as
conditional; see `provenance/m6-foundation/RVL-180.json` for the condition, the
artifact digest and the access record.

Confidence markers: **observed**, **documented**, **inferred**, **unknown**.

**There is no read marker in this document, and that is the point.** No source
text of this project was read, fetched, decompiled or opened. No compiled class
entry was opened either. Everything below comes from four places: the M5
inventory records, the pinned artifact's non-code entries listed and read as
documents, the upstream project's public description fetched over the network,
and inference from those. A specification written this way states what the entry
declares and what its dependents must be given. It cannot state what the entry
computes, and §12 is a long list because of it.

---

## 1. What this entry is

A shared library with no gameplay of its own. It contributes no recipe, no loot
table, no advancement, no worldgen feature and no command function to any world
(**observed**, all seven counted as zero in the catalogued surfaces). It ships no
model and no sound (**observed**). What it does ship is code, a small block of
shared-namespace tags, one language document, twenty-one interface images and one
bundled general-purpose library.

Its own description of itself is one sentence: a library of systems that make
several aspects of modding easier, naming three-dimensional mathematics and
transformations, model rendering, packets, configuration, colours and bytecode
manipulation (**documented**, from the artifact's mod descriptor and repeated
almost verbatim in the public repository landing page). That sentence is the
whole of the public documentation. There is no reference manual, no facility
list and no integration guide (**documented** — the landing page's remaining
content is distribution channels).

Size, counted from the archive listing (**observed**):

| | |
| --- | --- |
| Compiled entries in the outer archive | 522 |
| Compiled entries in the bundled library | 284 |
| Tag documents | 34 |
| Interface images | 21 |
| Language documents | 1, shipped twice |

The heuristic surface census attributes eighteen of those compiled entries to
networking and none to persistence (**observed**, and the census names its own
method as a class-path heuristic, so both numbers are indicative rather than
counted behaviour). A class-path heuristic counts compiled entries filed under a
package name, which means both numbers describe where the original's author put
its files and nothing further: this is the original's structure, and the
observable consequence is none, because no document in the archive names a
channel, a stored value or any other behaviour either number would imply. Do not
port the shape. A counterpart should treat "networking exists here and saved-data
machinery probably does not" as a hypothesis, not a finding, which is why §11
files the networking facility under what is named but not specified rather than
under what to implement.

## 2. What the pack's dependents observe

Seven pack entries depend on this one, every edge required rather than optional,
and every edge declared on both sides (**observed**, from the dependency graph).
No dependent declares it optionally, and no dependent outside the pack is in
scope. That makes this a foundation seed: the wave admits it with no dependency
of its own, and seven entries cannot load at all without it.

The seven split into two version floors: five require at least the minor version
this artifact carries, two require one patch below it, and all seven cap at the
next major version (**observed**). A counterpart therefore has to present a
version identity that satisfies a range, not merely exist. Which of the seven is
the ceiling on any given change is **unknown** without reading them.

**What each dependent actually calls is unknown.** The graph records that an edge
exists, not what crosses it. Nothing in this document was derived from a
dependent, and a counterpart cannot learn the required facility set from the
inventory alone. The honest statement of the integration risk is that seven
entries depend on a library whose surface has been catalogued from the outside,
and the first thing a counterpart will discover is a facility no document names.

## 3. What the entry declares to the loader

From the mod descriptor (**observed**):

- One mod, one loader kind, a loader-version floor expressed as an open-ended
  range, two authors, a display name and a description.
- Two platform dependencies, both required and both on both sides: the mod
  platform at a minimum version, and the game at an exactly pinned version. The
  exact pin matters. This artifact declares itself to run on one game version and
  no other, so the compatibility declaration a counterpart writes is a point, not
  a range, unless the counterpart is deliberately broader.
- No dependency on any other mod. Nothing in the pack is a prerequisite of it.
- An issue tracker, a version-check endpoint and a distribution page. The
  version-check endpoint is a live network call keyed to the game version
  (**inferred** from its shape; whether the entry actually calls it at runtime is
  **unknown**, and a counterpart must not).

The archive also carries an access-widening document of seventy-seven directives
— thirty-nine widening a member to public, thirty-three widening a field to
public, three to protected and two protected fields (**observed**, counted from
the document's directive column without reading the names) — and one
bytecode-transformation configuration declaring five client-side transformations,
a transformation plugin, a target environment of default and a Java 17
compatibility level, with no server-side or common list at all (**observed**).

Two things follow for a counterpart. First, this entry reshapes the host before
its dependents run: seventy-seven host members that are not normally reachable
become reachable, and any dependent may be relying on that rather than on this
entry's own code. What a counterpart owes there is **unknown** and is exactly
what the mixin-integration and cluster-integration tests exist to find. Second,
every declared transformation is client-side, which is evidence about sides and
is taken up in §6.

**One inventory discrepancy, recorded rather than resolved.** The M5 surface
census records two access transformers and no transformation configuration for
this artifact; the archive listing holds one access-widening document and one
transformation configuration (**observed**, both). The census's counting rule is
not stated in a way this document can reconcile, so which is right is
**unknown**. A reader who needs the number should count the archive.

## 4. What it registers into the game's data

The whole of the entry's data contribution is thirty-four tag documents in the
conventional shared namespace, and nothing else (**observed**).

The shape is two aggregates and thirty-two leaves:

- A block aggregate naming sixteen colour sub-tags, and an item aggregate naming
  the same sixteen (**observed**, both read in full; each is a values list of
  sixteen tag references and nothing more).
- Sixteen block leaves and sixteen item leaves, one per dye colour, each a values
  list (**observed**).

This is a compatibility contribution rather than content: it defines a
conventional grouping that the base game does not define, so that any mod
matching on "wool of a given colour" or "any wool" has a tag to match against.
Both the aggregate and the per-colour leaves are addressable, and a dependent or
a pack author may write either.

**A counterpart must provide all thirty-four.** The tag-parity test is against
this set. The aggregates must resolve through the leaves rather than listing
blocks directly, because a third party adding a coloured block to a leaf expects
the aggregate to pick it up. What each leaf lists is **observed** for the
aggregates and **unknown** in detail for the leaves, which were listed but not
each read; a counterpart should read the sixteen it ships against the artifact's
sixteen rather than assume the obvious membership.

The entry declares two data namespaces and one asset namespace (**observed**).
The second data namespace is the shared one the tags live in; the first is its
own and holds only the language document.

## 5. What it presents to a player

A player never encounters this entry as content. It reaches a player through two
things, both recoverable from the language document's eighteen keys
(**observed**, read in full).

**Three commands** (**observed** from their message keys; **inferred** that each
is a command rather than another surface, from the key prefix and the message
wording):

1. An entity count, reporting either a total or that none was found.
2. A memory-reclamation command reporting a before and an after reading around a
   collection it performs. This is a diagnostic that acts on the process.
3. A bulk entity removal, reporting a total killed, a per-kind line, a "found
   none" failure, and a distinct refusal for an attempt that would kill players.
   The refusal is a behaviour a counterpart keeps: the command declines the
   player case rather than executing it.

Whether these are client-side, server-side or both, and what permission level
each requires, is **unknown**. The message keys carry no side and no permission,
and nothing else in the archive's documents says. A counterpart must decide it,
and the safe decision for the second and third is server-side with an operator
requirement, because both act on a running world.

**Two screen widgets** (**observed** from their labels):

- An energy display titled as energy storage, labelling a capacity and a stored
  amount, with a unit of RF.
- A fluid display titled as fluid storage, labelling a capacity, a contained
  fluid and a stored amount, with a unit of mB.

Both are read-only presentations of a quantity a dependent supplies. The units
are compatibility-visible in the weak sense that a player reads them; a
counterpart uses the same two.

The language document is shipped byte-identically in both the asset tree and the
data tree (**observed**, confirmed by the build cache index, which records one
digest against both paths). Only one of the two is the one the game loads;
which is **inferred** to be the asset copy and the data copy **inferred** to be
a generation artefact. A counterpart ships one. The language-parity test is
against these eighteen keys.

## 6. Sides

Every dependency edge in the graph, in both directions, is declared for both
sides (**observed**). The layout heuristic classifies the artifact as both
(**observed**, and it names itself a heuristic).

Against that, every declared bytecode transformation is client-side and there is
no server-side or common list (**observed**), twenty-one of the entry's
twenty-one images are interface images (**observed**), and both of its player-
facing widgets are screen widgets (**observed**).

The honest reading: **the entry loads on both sides and a large part of what it
does is client-only** (**inferred**). A counterpart must load on a dedicated
server, because seven dependents declare it required on both sides and one of
them failing to find it there is a hard load failure. What it must actually *do*
on a dedicated server is **unknown** and is what the side-matrix test has to
determine empirically.

A counterpart must not take the client-heavy evidence as licence to make the
server half a stub. The eighteen networking-attributed entries of §1 and the two
world-acting commands of §5 both point the other way.

## 7. Configuration

The entry declares a configuration facility in its own one-sentence description
(**documented**) and ships no configuration document in the archive
(**observed**). The pack ships no configuration override for it either: the pack
overlay records neither a configuration file nor a script for this entry
(**observed**).

What follows is that either the facility is offered to dependents rather than
used for the entry's own settings, or the entry writes a default document on
first run that the pack never edits. Which is **unknown**. A counterpart
therefore has no configuration schema to reproduce and no default values to
match, and should offer a dependent-facing configuration facility only if a
dependent turns out to need one.

**Any file the entry writes outside the world is unknown.** Nothing in the
non-code documents names a path, and the heuristic census attributes no compiled
entry to persistence. A counterpart that writes nothing outside Ravel's own
storage diverges from nothing this document can see.

## 8. Assets and the resource pack

The archive declares itself a resource pack at the format number matching the
pinned game version, with a short description (**observed**).

Twenty-one images in one asset namespace, all interface (**observed**, listed and
counted, none opened):

- Five pointer images: a vertical resize, a horizontal resize, two diagonal
  resizes and a drag.
- Six widget images: an empty and a full energy bar, two slot sizes, and an empty
  and a full progress arrow.
- Ten frame images: a bordered and a borderless panel background, and eight
  button states across pressed, highlighted, disabled and borderless treatments.

One atlas document declares a single source: a directory, stitched under a
prefix (**observed**). So the interface images are addressed as atlas sprites
rather than as individual textures, and the six widget images and ten frame
images are sized to be scaled rather than drawn at a fixed size (**inferred**
from the nine-slice-shaped naming and the presence of a dynamic group; not
confirmed, because no image was opened).

**Rights, and what a counterpart ships.** These twenty-one images are the
entry's texture surface, which M5 records as permission-required. Nothing
upstream is shipped. A counterpart draws its own equivalents from reference under
`policies/source-access.json` and records each in the package's derivation
record. The asset-pipeline test is against a counterpart providing an equivalent
sprite set through Ravel's own asset path, not against pixel parity.

## 9. The bundled library

The archive bundles one further library as a nested archive, declared with a
group, an artifact name, an exact version, an accepted version range and a flag
saying it is not obfuscated (**observed**, from the bundling metadata document).
It holds two hundred and eighty-four compiled entries and one logging-framework
plugin index, and its package layout names logging, reflection, document
serialisation, collections, input and output, bytecode and network download
groups (**observed**, from the archive listing; nothing in it was opened).

Two consequences.

First, it is a general-purpose Java utility library and not part of this entry's
behaviour. A counterpart written in Rust needs none of it: the standard library
and Ravel's existing dependencies cover that ground. The nested-library-provision
test is about whether anything *else* in the pack expects that library to be on
the class path because this entry put it there. Whether anything does is
**unknown**.

Second, its version range is declared, which means the loader may resolve a
different build of it if another artifact bundles an overlapping range. That is a
platform mechanism a Ravel counterpart does not participate in, and a counterpart
provides nothing for it.

## 10. Networking

Eighteen compiled entries are attributed to networking by the class-path
heuristic (**observed**, indicative). The entry's own description names packets
as one of its facilities (**documented**).

**Both of those are §1's hypothesis rather than a finding.** One is a count of
files filed under a package name, the other a clause in a one-sentence
description, and neither is behaviour this document recovered. What follows is
therefore a section about a facility a file layout suggests exists, written to
say what cannot be known about it.

That is the entirety of what is knowable without reading. **No channel
identifier, no protocol version, no payload identifier, no packet direction and
no wire format is recoverable from any non-code document in the archive**
(**observed** — every document was read and none names one).

This matters more than any other unknown here. A networking facility offered to
dependents is a wire contract, and two peers agree on a packet only if both
derive the same identifier. A counterpart cannot derive it. The networking-probe
test can only observe what a running instance sends, and a counterpart's channel
identity therefore has to be established by observation or by agreement with the
dependents, not by specification. Until it is, no counterpart of this entry can
be wire-compatible with an unmodified dependent.

**Anything a counterpart builds here is a design it invents.** This section
recovers no contract, so a channel identifier, a framing, a payload set or a side
rule appearing in a counterpart is that counterpart's own invention and binds no
one. A later reader must not take an implementation of this section as evidence
of what the original does, and §11 files this facility under what is named but
not specified for exactly that reason.

## 11. What a counterpart must provide

Ordered by how well this document supports it.

**Supported by observation, implement as specified:**

1. The thirty-four tags of §4, aggregates resolving through leaves.
2. The eighteen language keys of §5, covering three commands and two widgets,
   with the player-kill refusal kept as a refusal.
3. An equivalent sprite set for the twenty-one interface images of §8, drawn
   fresh, addressed through an atlas-equivalent path.
4. A compatibility declaration satisfying a range whose floor is at or below the
   pinned artifact's version and whose ceiling is the next major (§2).
5. Loading on both sides, with the server half not stubbed (§6).
6. **Named but not specified, needs discovery before implementation (items 6–9):**
   Whatever the seven dependents actually call (§2).
7. Whatever the seventy-seven access widenings let dependents reach (§3).
8. A networking facility with a wire identity that cannot be derived from any
   document (§10).
9. Three-dimensional mathematics, transformations, model rendering, colours and
   configuration, each named in one sentence of public description and nowhere
   else (**documented**, §1).
10. **Provides nothing:** The bundled utility library (§9) and the version-check network call (§3).

A counterpart built from items 1 to 5 alone satisfies the tag, language, asset
and side tests and will not load a single one of the seven dependents. That is
the true state of this specification and it should not be softened.

## 12. What this specification does not specify, and what was not read

**Nothing was read.** No source file, no repository, no decompiled tree, no
class entry, not one byte of compiled code. The M5 rights triage records this
entry's code surface as permission-required under a weak-copyleft licence and its
`sourceUse` as conditional, and this entry's plan elects black-box
respecification with `readsSource` false. `policies/source-access.json` would
permit a private reader to read source for a specification; this entry does not
rely on that permission, and the condition recorded against it in the provenance
is what governs here. The rights-method-audit test is against that.

What was used instead: the M5 inventory records; the pinned artifact's non-code
entries, listed in full and read where they are documents — the mod descriptor,
the pack declaration, the transformation configuration, the bundling metadata,
the language document, the two tag aggregates, the atlas document, the build
cache index, the access-widening document's directive column, and the licence
header; and the upstream project's public landing page fetched once over the
network. All are recorded in the provenance.

**Not specified here, because it cannot be:**

- Every algorithm, every data structure and every method contract in five
  hundred and twenty-two compiled entries. This document names facilities that
  documents declare and quantities that documents count. It states nothing about
  what any of that code computes, and a reader should not treat the absence of a
  behaviour here as evidence that the entry lacks it.
- The wire format (§10). The single largest gap, and the one that makes
  drop-in compatibility with the existing dependents unavailable today.
- The registration, rendering, mathematics, colour and configuration facilities
  named in one sentence of public description (§1). Nine words of documentation
  is not a specification of anything.
- Any dependent's use of this entry (§2). No dependent was read either.
- Which side each of the three commands runs on and what permission each needs
  (§5).
- Whether any configuration or out-of-world file is written, and where (§7).
- The membership of the thirty-two tag leaves in detail (§4).
- Any save-compatible identifier mapping. The names surface is unresolved in the
  provenance record, so a counterpart's alias declaration is empty and no
  existing world is loadable by it.
- The two-versus-one integration count discrepancy of §3.

**One author, one pass, no second reader.** This document was written by a single
hand and nothing contradicted it. The observed/documented/inferred/unknown
markers and this section stand in for the second reader and are weaker than one.
They are weaker still than the markers on a specification written from source,
because a reader who saw the code could at least be wrong about something
specific.
