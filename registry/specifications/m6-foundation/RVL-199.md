# RVL-199 — behaviour specification

Wave: `waves/m6-foundation.json`. Method: source-informed reimplementation.
Rights: the upstream project's repository root carries an MIT licence file, and
its readme links to it as the project's licence; see
`provenance/m6-foundation.json` for the pinned revision and digest.

Confidence markers: **read**, **inferred**, **unknown**.

---

## 1. What this entry is

The only content mod among the five. It adds a farming progression: crops that
grow into refined materials, gear made from those materials, a set of processing
machines, and an upgrade system that modifies tools and armour. It depends on
RVL-162 (**read** — its build declares the dependency and its own version pins
that library's version).

It carries by far the most data of the five: several thousand data and asset
files against roughly three hundred source files (**read**).

**A prose specification is the wrong medium for its content catalogue** and this
document does not attempt one. What follows specifies the *systems* — the rules
that decide what the content does — and states plainly that the catalogue itself
(which crops exist, at which tier, from which recipe, dropping what) is data.
That data is already inventoried per artifact in the private inventory and is
where an implementer must take it from. §8 makes the split explicit.

---

## 2. The extension model

The entry is built to be extended by other mods, and three of its registries are
public (**read**):

- crops,
- tool and armour upgrades,
- entity-essence kinds.

A mod extends it by publishing a marked plugin class. Each plugin gets, in order
(**read**):

1. a configuration callback;
2. a registration callback and then a post-registration callback for crops;
3. the same pair for upgrades;
4. the same pair for entity-essence kinds.

Every callback has a do-nothing default, so a plugin implements only what it
cares about. The paired shape is load-bearing: the post-registration pass exists
so a plugin can react to entries other plugins registered in the first pass
(**inferred** — nothing states it, but it is the only reason for the pairing).

**unknown**: the ordering between plugins. Not determined.

## 3. Crops

### 3.1 Tiers

A **crop tier** is a named group of crops sharing progression level and
appearance. Each tier carries (**read**):

- an identifier, whose namespace names the mod that created the tier and whose
  path is the tier's short name;
- a numeric level, where higher means further along;
- a display colour and a text colour;
- a display name, defaulting to a translation key formed as
  `cropTier.<namespace>.<name>` and always rendered in the tier's text colour;
- the block that counts as this tier's **effective farmland**;
- the refined item this tier's crops produce;
- whether this tier's crops respond to the mod's two growth accelerants —
  default yes;
- whether this tier's crops can drop a second seed — default yes;
- a base secondary-drop chance — default 0.1.

Six tiers are defined by the entry itself: five numbered one to five, and one
further tier at level one used for a different progression line (**read**). Their
colours and text colours were read and are recorded in the private inventory
rather than here.

A block is this tier's effective farmland if it is the tier's own farmland block
**or** if it carries a published block tag meaning "always effective farmland"
(**read**). The tag is the extension point; a counterpart must honour it.

### 3.2 Types

A **crop type** distinguishes progression lines — one producing materials, one
producing entity essences (**read**). Each type carries an identifier, a base
model location for its growth stages, and the seed item used in its recipes.

### 3.3 Growth rules

A crop grows on a random tick only if **all** of the following hold (**read**):

- if the crop declares a required foundation block, the block two below the crop
  is that block;
- if the "requires effective farmland" setting is on, the block directly below is
  effective farmland for the crop's tier — **except** for the tier-one base crop,
  which is exempt unconditionally;
- if the crop declares required biomes, the crop is in one of them.

The same three checks gate both accelerant-driven growth and the game's own
question of whether the crop is a valid accelerant target (**read**). A crop that
fails them is not merely slow: it never advances, and applying an accelerant does
nothing.

Crops never respond to the stock accelerant's success roll — that always fails
(**read**), so accelerating a crop is always deterministic given the checks above
pass.

Crops occupy a low collision shape rather than the stock crop shape (**read**).

### 3.4 Drop rules

When a crop is broken (**read**):

- Below full growth: one seed, nothing else.
- At full growth: one seed and one refined item, plus:
  - a **secondary chance** roll (§3.5) that, on success, makes the refined item
    two instead of one;
  - if the "secondary seed drops" setting is on, an independent roll at the same
    chance that makes the seed two instead of one;
  - an independent roll at a configured chance that adds one growth-accelerant
    item.
- If the loot context carries no position, none of the extra rolls happen and the
  drop is one seed and one refined item (**read**). This is observable — silk
  touch and some automation paths produce a positionless context.

The three rolls are independent draws, not one draw reused (**read**).

### 3.5 The secondary chance

Given the block directly below the crop (**read**):

- start at zero;
- if the crop's tier has secondary drops disabled, the chance is zero and nothing
  further applies;
- if the block below is any tier's essence farmland, add the crop's own base
  chance, or the tier's base chance when the crop does not override it;
- if the crop respects effective farmland **and** the block below is effective
  farmland for the crop's tier, add a further 0.1;
- clamp to at most 1.0.

Note the two additions are not exclusive: a crop on its own correct farmland gets
both. That is required behaviour.

### 3.6 Farmland conversion

An item that converts farmland behaves as follows when used on a block
(**read**):

- On stock farmland: the block becomes the item's target farmland, **preserving
  the moisture level**, a break sound plays, and one item is consumed.
- On some other tier's essence farmland, when the item declares a tier different
  from the existing block's tier: the same conversion happens, and with
  probability 0.25 the *previous* tier's refined item pops out above the block.
- On its own tier's essence farmland, or on anything else: nothing happens and
  the interaction passes through.

The moisture preservation and the 0.25 refund are both observable and both easy
to lose.

## 4. Upgrades for tools and armour

An **upgrade** is a named modifier applied to a tool or armour piece (**read**):

- Twenty upgrade target kinds are published, covering broad categories (tool,
  weapon, armour, staff) and specific item kinds (each stock tool and weapon
  shape, each armour slot, and the four extra tool shapes RVL-162 provides). Each
  kind has a display name from a translation key.
- An upgrade declares which target kinds accept it.
- An upgrade may carry attribute modifiers and may be area-of-effect, in which
  case it carries an offset describing the affected region.
- Applied upgrades are stored on the item as attached data.

**unknown**: how upgrades combine when several apply to one item, what the limit
is, and how conflicts resolve. Not read.

## 5. Entity essences

An **entity-essence kind** binds one or more entity types to a harvestable
essence (**read**):

- it carries an identifier, a set of entity type identifiers, a requirement
  expressed as a fractional quantity, a colour at fixed 80% opacity, and an
  enabled flag defaulting to on;
- an entity matches the kind when its type's identifier is in the set;
- its display name is either an explicit translation key formed as
  `mobSoulType.<namespace>.<key>`, or, when none is given, the description of the
  first entity type in the set, or, when that type does not exist, a fixed
  "invalid entity" message. **The resolved name is cached on first request**, so
  a kind resolved before its entity type is registered keeps the fallback name
  for the rest of the session (**read**). That is a defect; a counterpart should
  resolve lazily without caching a failure, and record the divergence.

The colour's fixed opacity is applied at construction and again on every later
change, so a caller cannot set a fully opaque colour (**read**).

## 6. Machines and their upgrades

The entry adds several processing machines, each with its own recipe kind. Seven
recipe kinds are published in its interface (**read**): refining, infusion, ore
infusion, enchanting, awakening, essence extraction from entities, and entity
spawning from essence. Each has its own data-driven recipe directory.

**Machine upgrades** form six ordered tiers (**read**). Five correspond to crop
tiers one to five; the sixth is a further step beyond the fifth and shares its
level and colour. Each tier states four numbers, and they are the whole of its
observable effect:

| tier | operation-time multiplier | fuel-use multiplier | fuel-capacity multiplier | added range |
| ---- | ------------------------- | ------------------- | ------------------------ | ----------- |
| 1    | 0.833                     | 2                   | 2                        | 1           |
| 2    | 0.625                     | 4                   | 3                        | 2           |
| 3    | 0.4                       | 6                   | 4                        | 3           |
| 4    | 0.125                     | 16                  | 5                        | 4           |
| 5    | 0.025                     | 48                  | 6                        | 5           |
| 6    | 0.005                     | 96                  | 7                        | 6           |

Each multiplier is applied to a machine's base value and **truncated to an
integer** (**read**). The truncation is required: it is why the highest tier's
operation time can reach zero for small base values, and a counterpart that
rounds instead changes speeds across the whole progression.

**unknown**: each machine's base values, its inventory layout, its fuel model,
and what happens at a zero operation time. Not read.

## 7. Configuration

Several settings were read in passing, each changing observable rules above
(**read**):

- whether crops require effective farmland to grow (§3.3);
- whether crops can drop a second seed (§3.4);
- the growth-accelerant drop chance (§3.4).

Others exist and were not read. The set of settings and their defaults is not
specified here.

## 8. Content is data, not specification

The following are **not** specified in this document, on purpose:

- which crops exist, their tiers, types, required foundation blocks, required
  biomes and secondary-chance overrides;
- which upgrades exist and what each does;
- which entity-essence kinds exist, their entity sets, requirements and colours;
- every recipe, loot table, tag, biome modifier, model, texture, translation and
  guidebook page;
- the names of any of the above.

They are catalogue data. Reproducing them through prose would be both useless and
exactly the transliteration-through-prose failure the clean-room process exists
to prevent. An implementer needs the *systems* above and then a data set; where
Ravel's data set comes from is a separate decision this document does not make,
and it has a rights dimension the wave manifest's per-surface verdicts already
speak to.

The one thing to carry forward is the shape: every item in the catalogue is
expressible as declarations against §3–§6, and any that is not is a system this
document missed.

## 9. What this specification does not specify

- **Everything in §8.**
- **Upgrade combination rules** (§4), marked unknown.
- **Machine internals** (§6), marked unknown: base values, inventories, fuel,
  and behaviour at zero operation time.
- **The full configuration set** (§7).
- **The client surface**: screens, renderers, tinting, the guidebook. Roughly a
  seventh of the source, unread.
- **The optional integrations** with other mods. Present, unread.
- **Worldgen.** Present as biome modifiers and a small amount of source, unread.
- **The seven recipe kinds' fields and semantics.** Their existence and purpose
  are recorded; none of their schemas was read. This is the largest single gap
  and the wave's recipe-parity test lands squarely on it.
- **Coverage.** Read in full: the public extension interface, crop tiers, crop
  types, the crop block's growth and drop rules, the secondary-chance rule, the
  farmland conversion rule, the upgrade target kinds, the entity-essence kind,
  and the machine upgrade tiers. Everything else: listed, not read.
