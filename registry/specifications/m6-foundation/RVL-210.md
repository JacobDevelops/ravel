# RVL-210 — behaviour specification

Wave: `waves/m6-foundation.json`. Method: source-informed reimplementation.
Rights: the upstream project's repository root carries an MIT licence file, read
at the source; see `provenance/m6-foundation/RVL-210.json` for the pinned
revision, the licence identity and the digest.

Confidence markers: **read**, **inferred**, **unknown**.

This entry is a foundation seed admitted on its own rubric, and it depends on
nothing else in the inventory (**read**, from the wave manifest). It is the
deepest thing in its family by some distance. Eight declared dependents in the
pinned pack name it as a required dependency on both sides, and those eight
resolve to five admitted counterparts: RVL-132 inside this wave, and RVL-085,
RVL-188, RVL-216 and RVL-241 outside it (**read**, from the pinned dependency
graph; three of the eight declarations are companion integrations shipped inside
a sibling's own artifact rather than separate entries). What those dependents
actually consume is §17, and §5 to §16 are what §17 rests on.

---

## 1. What this entry is

A shared library with almost no gameplay of its own. It ships no block, no item,
no recipe document, no tag document, no loot document and no advancement
document, and the only things a player can encounter directly are two particle
effects, one demonstration screen reachable through a command, and a cosmetic
effect granted to a fixed list of named accounts (§9) (**read**).

Everything else it publishes is machinery for the mods that declare it: a
declarative content-registration framework covering thirty-one kinds of
registrable thing, a settings framework those mods declare their own settings
through, a general-purpose command transport with a reflective wire format, a
screen-to-client value channel, a generic quantity-collection library with
indexed lookup, a structured-data query language with its own grammar, a
multiblock shape detector, an annotation-driven saved-data mechanism, a
registry-dumping service, and an in-game manual engine.

**Size.** The pinned artifact is built from 591 source files: 237 portable ones
and 354 belonging to the host platform the pinned artifact targets (**read**).
The repository also carries 113 files for two other host platforms that this
artifact is not built from, and 84 test files that are not shipped (**read**).
Its shipped resources are 30 translation documents, 5 images, 3 item and block
model documents, 2 particle definition documents, 1 manual document, 1 schema
document and 1 empty structure template (**read**). There is no block-state
document, no sound file and no data-pack content of any kind.

The division of those files into a portable half and a half belonging to the
host platform is the original's source-tree structure; a dependent declares
against the one host it is running on, so the observable consequence is none. Do
not port the shape.

The proportion that matters to scoping a counterpart is different from the file
count. Roughly a third of the source is presentation the counterpart does not
owe anyone: a hand-rolled widget toolkit, its model loading, its render helpers
and the manual engine's page layout. What a dependent can observe from outside is
the registration contract, the wire contracts, the collection semantics and the
query grammar.

The entry declares itself mandatory and present on both sides, with the game and
the loader as its only declared requirements (**read**).

### 1.1 Ravel disposition

Ravel already owns most of what this entry exists to provide, and owns it better.
Content declaration and registration, settings declaration and resolution,
saved-data ownership, side isolation, screen drawing and network payload
registration are public Ravel facilities. A counterpart expresses the behaviour
below through them rather than rebuilding the framework, and the framework is
where most of the 591 files go.

What survives as counterpart work is the part a dependent can observe and would
break without: the wire contracts (§6, §7), the collection and storage semantics
(§10), the query grammar (§11), the shape detector (§12), and the registration
vocabulary of §5 that dependents declare against.

Three things are host-blocked or policy-blocked rather than declined, and a
counterpart records them rather than stubbing them: the access widening of §16,
the outbound fetch of §9, and the interface vocabulary of §10 whose declarations
were not in the fetched archive.

## 2. Side, lifecycle and what happens when

The entry runs on both sides (**read**).

- **At construction** it claims three of its own service registries: one for
  registry-dumping producers, one for manual documents, and one naming the places
  an item store can be found. It then declares its settings documents and its
  sixteen declared entries (§4, §5), and asks the loader for the lifecycle points
  it needs.
- **At common setup**, on every side, it populates the registry-dumping
  producer set (§14) and calls a per-platform loader that adds this platform's
  types to two further tables: the persistable field-type table (§13) and the
  wire codec table (§6). The portable entries of those two tables are not loaded
  here; each table holder fills them in a static initialiser, so they exist as
  soon as the holder is first touched (**read**). It registers its own
  demonstration manual document. It installs three advancement-trigger event
  hooks.
- **On a client only**, at common setup, it additionally loads the crafting
  helper tables. This is a side test at runtime rather than a client-only
  declaration, so on a dedicated server that table is never built (**read**).
- **At command registration** it builds one command tree rooted at its own name
  and hangs seven subcommands off it (§15).
- **At server start** it begins the outbound fetch of §9.
- **At server about-to-start, started and stopping** it drives the saved-data
  objects any dependent registered with it: reset, then load and notify, then
  save (**read**).
- **At load complete** it latches a flag that dependents can read to ask whether
  loading finished.

**Ordering that is load-bearing.** The platform additions to the wire codec
table and to the persistable field-type table are added at common setup, and both
the command transport and the saved-data mechanism read those tables. A dependent
that sends a message or persists a field of a platform type before common setup
finishes has no entry to read; the portable entries are already there, because
their static initialiser runs on first touch of the holder (**inferred**; the
source states the load point but states no guarantee about it).

## 3. Settings

The entry declares two settings of its own, both in the client-scoped document,
both under one grouping, and both meaningful only inside a development
environment (**read**): whether to add a shortcut to the main menu that opens a
scratch world, and whether to silence music at startup. Neither affects a shipped
game.

This is the whole of its own configuration surface, and it is worth stating
plainly because the settings *framework* it publishes is one of its largest
products. The framework is §5; the entry barely uses it on itself.

Both settings are marked as changeable through the command tree at runtime, which
is a property of the framework rather than of these two settings (§5.3).

## 4. What it registers

Sixteen declared entries, resolving to fifteen registrations and one
settings-only declaration that registers nothing (**read**). Counted from the
tree twice.

**Two particle types**, each with a definition document and one of them with an
animated texture: a soft round glow, and a coloured falling droplet.

**Four item data component kinds**: a capacity number, a stored-energy number, a
single-fluid content record, and an embedded item store.

**Three advancement trigger kinds**: a screen was opened, an item was crafted,
and the first item belonging to a given mod was obtained by a player.

**Three command argument kinds**: a settings-property name, a diagnostic message
name, and a generic enumeration member.

**One menu type**, for the demonstration manual screen of §14 that only a command
opens.

**One loot modifier kind**, which injects an item into a loot result.

**One item capability declaration**, for a fluid store whose capacity is read
from the capacity data component above.

The seven identifiers among these that a dependent or a saved world could store —
the four data component kinds and the three trigger kinds — are exactly what the
names surface in the provenance record does not clear. A counterpart that is
save-compatible with the original is what that record cannot clear, and this
specification therefore names none of them.

## 5. The content-declaration and registration framework

This is the entry's largest product and the thing every dependent is built on.

### 5.1 The declaration vocabulary

A dependent declares a piece of content as a **declaration object**: a value that
names the kind of thing being registered, carries the name it registers under,
and carries whatever construction the kind needs. The framework then registers it
at the right lifecycle point for that kind, on the right side, in the right
registry.

The framework admits **thirty-four kinds** on the host the pinned artifact
targets (**read**): blocks, block entities, items, entities, menus and their
screens, particles, recipes, recipe kinds, sound events, status effects,
villager professions, creative tabs, armour materials, enchantment effect
component kinds, enchantment entity effect kinds, loot conditions, loot
functions, loot number providers, loot score providers, loot data providers,
world features, world structures, structure pieces, trunk placers, foliage
placers, command argument kinds, advancement trigger kinds, data component kinds,
capability declarations, a settings-only declaration that registers nothing,
fluids, loot modifiers, biome modifiers and a recipe-condition kind. The
original's source tree carries this vocabulary as two overlapping sets, one per
host platform, differing by four additions and one omission; that is the
original's structure, and a dependent sees the one vocabulary of the host it is
running on. Do not port the shape.

**Behaviour a counterpart owes, not structure.** Three rules make this a contract
rather than a convenience (**read**):

- Every declaration is separately **disableable** through the settings document.
  A declaration that is switched off is never registered, and the framework
  refuses the switch for declarations marked as not disableable, raising rather
  than silently ignoring the request.
- The registration order within a kind is declaration order, and the framework
  registers all declarations of one kind before moving to the next.
- A declaration carries an optional client-side companion, and that companion is
  loaded only on a client. This is a declaration-time split rather than a runtime
  side test, and it is the mechanism a counterpart should keep: it is why the
  library's client-only registration never runs on a dedicated server.

### 5.2 Settings declaration

A dependent annotates a static field with its category, its comment, the document
it belongs in, and whether it can be changed at runtime. The framework collects
those into per-document settings files, one file per scope, and resolves them
before the dependent's own setup runs.

The scope vocabulary is three values: client, server, and common (**read**). What
a counterpart must preserve is that a setting's scope decides which file it lands
in and therefore who may change it, not merely where it is written.

### 5.3 Runtime settings changes

A setting marked changeable can be read and written through the command tree
while the game runs, addressed by its declared property name through the
settings-property argument kind of §4. Writing one takes effect immediately
against the in-memory value (**read**). Whether it is written back to the file is
**unknown**; the read did not reach that path.

## 6. The command transport and its wire format

The entry publishes a general-purpose message channel that dependents send their
own messages over, and the encoding is the behaviour rather than an incidental
choice, so it is stated here.

A message is a value whose fields are individually marked for transport. On the
wire, the marked fields are written **in a defined order** and read back in the
same order, with no field names, no lengths and no framing between them: the
receiver's field order is the only thing that tells it what it is reading
(**read**).

**The order is load-bearing and it is not declaration order.** It is: walk the
concrete message type upward through its ancestors, stopping before the framework
base; within each level take that level's own marked fields sorted by field name
in ascending order; concatenate the levels in the order walked, most-derived
first (**read**). The sort is deliberate, and the source says why: the language
gives no guaranteed order for a type's declared fields, and two peers that
disagreed about the order would mis-decode every message.

A counterpart that keeps this transport must keep this order exactly, because a
dependent's message is only decodable if both ends agree, and this is what both
ends of the original agree on. A counterpart that does **not** keep it needs its
own explicit ordering and cannot interoperate with an unmodified original.

Per-field encoding comes from a table of type-to-encoder entries keyed by
declared field type and extensible by a dependent for its own types (**read**).
The portable entries are written by the table holder's static initialiser; only
this platform's additions are loaded at common setup (**read**). The portable
entries are a plain enumerated list in that holder and this specification chose
not to enumerate them; they were seen and are not unknown.

The entry registers **thirteen** message kinds of its own: a resource reload
request, the cosmetic effect of §9, a screen button click, a screen value update
(§7), a request and a reply for a player's stored data, a request and a reply for
whether a player has unlocked an advancement, an advancement reward claim, and
four diagnostic round-trip messages used only by the diagnostic command
(**read**). It also publishes a player-position message as an abstract base for
dependents to extend rather than as a message it sends, and that base is not one
of the thirteen (**read**).

Delivery targets a counterpart must reproduce: to one player, to every player, and
to every player within a radius of a point in a level. The cosmetic effect uses
the radius form with a radius of fifty blocks (**read**).

## 7. The screen value channel

A screen and its server-side counterpart share a small keyed store of values,
addressed by an integer identifier the server allocates, and the server pushes
changes to the viewing client over the transport of §6 (**read**).

Each value is boxed inside a per-identifier compound under one fixed key. There
are **seven** readers, and every one of them follows the host's own absent-value
defaults rather than raising (**read**):

- The integer and boolean readers yield zero and false both when the identifier
  is absent and when the stored value is of the wrong kind.
- The string reader yields nothing at all only when the identifier is **absent**.
  When the identifier is present but the boxed value is not a string, the
  underlying read returns the empty string, so the reader yields an empty string
  rather than nothing.
- The display-text list reader behaves the same way: nothing when absent, an
  empty list when present but of the wrong kind.
- The raw reader hands back whatever is under the fixed key without a type, and
  the single display-text reader reads the boxed value as a string and hands it
  to the host's deserialiser. Both yield nothing when the identifier is absent
  **and** nothing when it is present with a value of the wrong kind, so neither
  preserves the distinction.

Where the distinction survives it is a real observable difference and a
counterpart has to preserve it, because a dependent screen distinguishes "not
sent yet" from "sent as empty" on exactly this. A counterpart also owes the two
readers that collapse the two cases, because a dependent reading through one of
those cannot tell them apart in the original either.

## 8. Screens, menus and inventories

The entry publishes a menu base that dependents build their screens on, and the
parts of it that are behaviour rather than presentation are (**read**):

- A slot-range vocabulary letting a menu declare which of its slots are the
  player's, which are the machine's, and which are output-only, which is what
  makes shift-click transfer behave without each dependent writing it again.
- An item-store abstraction with a dirty-marking callback, so a store can be
  embedded in a data component or a block entity and notify its owner on change.
- An indexed store wrapper that answers "which slots hold something matching this
  prototype" without scanning, backed by an index maintained on write.
- A store-change counter that increments on every mutation, which dependents poll
  instead of comparing contents.

The indexed wrapper and the change counter are the two a dependent can observe
the cost of, and they are why RVL-132 names this entry at all (§17).

## 9. The outbound fetch at server start, and the cosmetic effect

This is small, it is unusual, and a counterpart must not reproduce it as written.

The entry hard-codes **five player account identifiers**. A player whose account
matches one of them gets a purely cosmetic ring of particles broadcast to everyone
within fifty blocks (**read**). It is decoration for specific real people and
nothing depends on it.

At **server start**, on every server, the entry starts a background thread that
fetches a plain-text document over the network from a fixed address on the
author's public code-hosting account, parses one account identifier per line
taking the first comma-separated field, and adds each one to the same allow-list
(**read**). The fetch is unconditional: no setting gates it, no consent is asked,
and a failure is logged at warning level and otherwise ignored. It runs exactly
once per process, guarded by a latch.

**Ravel disposition.** A counterpart reproduces neither half. The hard-coded list
is other people's identity and is not ours to carry; the fetch is unannounced
outbound network access from a library a pack author installed for its collection
types. If the cosmetic effect is wanted at all, it belongs behind a setting that
defaults off and a list the server owner writes. This is a deliberate behavioural
divergence and it is recorded here rather than left for an implementer to
discover.

The entry also carries a second, older outbound path: a version-check service
that fetches a three-line text document per registered mod and shows an in-chat
notice when a newer version is named. Its source marks it superseded by the
platform's own update mechanism, and the entry registers no mod with it at this
revision, so it does not run (**read**). A third path, an analytics beacon, is
marked unused and is unreachable (**read**).

## 10. The generic quantity framework

This is the part RVL-132 is built on and the largest single body of behaviour in
the entry: 42 collection files, 7 storage files, 3 difference files and 2 recipe
files, with 44 test files exercising them (**read**). All of them live in the
platform-specific half, not the portable one, as does the query language of §11
(**read**); the 44 are part of the 84 the module ships in total (§1).

**The abstraction.** A *quantity kind* is a thing that can be counted, matched
and stored: items, fluid volumes and energy are the three the family uses, but the
framework is written against the abstraction and not against those three. A kind
supplies a matcher that decides equality under a caller-chosen set of match
conditions, a hasher consistent with that matcher, and a serializer.

**The collections.** Over that abstraction the entry publishes list, set and map
types with the usual semantics, plus three that are not usual and that a
counterpart owes exactly (**read**):

- A **classified** collection that partitions its contents by one or more
  category functions derived from the kind, so a lookup restricted to a category
  scans only that category's partition rather than the whole collection. Single-
  and multi-category variants exist and differ in whether a lookup may intersect
  partitions.
- A **collapsed** collection that stores one entry per distinct instance with a
  summed quantity rather than one entry per addition, so adding the same thing
  twice yields one entry of doubled quantity and iteration yields one element.
- A **summing view** over an uncollapsed collection, which presents that
  collection as if collapsed without copying it.

**Matching is parameterised, and that is the subtle part.** Equality is not a
property of the stored value; it is a property of the query. The same collection
answers differently depending on which conditions the caller asked to match on,
and a classified collection may only use a partition when the query's conditions
are a superset of the partitioning conditions (**inferred**; the source
implements the restriction, and does not state it as a rule).

**Storage moves.** Over the collections sits a storage interface with insert,
extract and a simulate flag, plus a helper that moves a quantity from one store
to another. The move semantics a counterpart owes (**read**): a move is attempted
as a simulation first, the simulated result decides the real amount, and the real
insertion is then performed. If the real insertion accepts less than the
simulation promised, the helper first tries to put the shortfall back into the
source, and returns a reduced moved quantity when that recovery succeeds. Only
when the recovery also fails does it raise a dedicated inconsistency error, so a
partial move completes rather than raising. Slotted and slotless stores both
exist and the slotted form additionally guarantees which slot a result came
from.

**A difference tracker** compares two snapshots of a collection and yields
additions and removals, which is how the family sends store contents to a client
incrementally rather than resending the whole store.

**A gap in this section.** The interface declarations for the quantity kind, its
matcher, its serializer and the storage interfaces are **not in the fetched
archive**. They live in a separate interface package that the build pulls in as a
sub-repository and compiles into this same artifact, and the archive form of the
pinned revision carries the empty directory rather than the contents (**read**,
from the sub-repository declaration and the empty directory). Sixty-seven files in
the fetched tree use that vocabulary. What is written above is therefore taken
from the use sites and is **inferred** rather than read: the method names, the
exact signatures and the vocabulary of the conditions it matches on are
**unknown** at the pinned revision.

That gap has a consequence for the wave that is worth stating: the interface
package is published by the same author as RVL-132's own artifact, and the plan
row records RVL-210 as depending on nothing. Both can be true, because the
interfaces ship *inside* this entry's artifact rather than being resolved from
the dependent at runtime. But it means the shared vocabulary between RVL-210 and
RVL-132 is a third thing that neither plan row names, and whoever implements
either counterpart has to decide where it lives on the Ravel side before either
can compile. That decision is not this specification's to make and is flagged in
§18.

## 11. The structured-data query language

The entry publishes a query language over the host's structured-data trees, with
its own grammar and its own parser. This is a genuine language and not an
incidental helper, so it is specified as one.

A query is parsed left to right. At each position the parser tries a fixed,
ordered list of **twenty-two** expression handlers and takes the first that
matches a prefix at that position; a position no handler matches is a parse error
(**read**). Because the list is ordered and first-match wins, the order is part of
the grammar: the counterpart cannot reorder it and get the same language.

The twenty-two, in the order tried (**read**):

1. root,
2. length,
3. named child,
4. named child in bracket form,
5. parent,
6. all children,
7. current node,
8. list element by position,
9. list slice,
10. union of expressions,
11. parenthesised grouping,
12. less-than,
13. less-than-or-equal,
14. greater-than,
15. greater-than-or-equal,
16. not-equal,
17. equal,
18. string equality,
19. logical and,
20. logical or,
21. logical not,
22. filter expression.

Evaluating a query yields a **set of matches** rather than a single value, because
the wildcard, slice and union forms are many-valued. Navigation over the parsed
form is separately expressible, which is what lets a caller ask whether a path
*could* match without evaluating it against data.

The logical and, or and not forms are new at the pinned revision and are its
headline change (**read**, from the changelog at the pinned revision). A
counterpart targeting an earlier build of the same family would be specifying a
smaller language.

## 12. Multiblock shape detection

Given a set of block predicates and a starting position, the detector finds the
largest connected region of matching blocks and validates it against a list of
constraints (**read**). The constraints published are: exact size, minimum size,
maximum size, cube-ness, and exact, minimum and maximum counts of a particular
allowed block. A hollow variant requires the region's interior to be empty.

The result is either a validated region with its bounds, or a failure carrying the
position and the reason, which the family surfaces to the player as a message
naming what is wrong (**read**). A counterpart owes the failure detail, not just
the boolean: a dependent's whole player-facing experience of building a multiblock
is that message.

The traversal order and the tie-breaking when two regions are equally large are
**unknown**; the read established the constraint vocabulary and the result shape
and did not follow the search.

## 13. Saved data and persistable fields

Two mechanisms (**read**).

**Annotated field persistence.** A dependent marks fields on a block entity or a
saved-data object as persistable. The framework writes them into and reads them
out of a compound automatically, dispatching per field through a type table loaded
at common setup and extensible by dependents. Each field is stored under its own
name, so the format is name-keyed rather than positional, which is the opposite of
the wire format of §6 and is the right choice for stored data.

**Per-world saved data.** A dependent registers a saved-data object with the
entry, and the entry drives it across the server lifecycle: reset before start,
load and post-load notification at started, save at stopping. One such object is
the entry's own: a table of named counters that hand out monotonically increasing
integers unique within a world, which dependents use to allocate durable
identifiers.

A counterpart implements both through Ravel's saved-data ownership rather than
rebuilding either, but owes the counter's guarantee: unique and increasing within
a world, surviving a restart.

## 14. Registry dumping and the in-game manual

**Registry dumping.** A service collects producers that can each serialise one
registry to a document, and a command writes them all out (§15). Seven
producers ship: plain crafting recipes, four cooking-recipe variants
(smelting, blasting, smoking and campfire cooking), and the translated display
names of every item and of every fluid (**read**). Dependents add their own. The purpose is external
tooling: a pack author dumps the game's registries to feed a recipe viewer or
a wiki.

**The manual engine.** An XML document describes a book of pages; the engine
parses it, resolves the referenced content, paginates it and draws it. It supports
conditional sections that appear only when a named mod is present, and reward
items that a player claims by reading a page. One demonstration document ships and
the entry registers it for itself; nothing but a command opens it (**read**).

Both are presentation-adjacent and neither is on a dependent's critical path. A
counterpart records the dumping service as behaviour a pack author may depend on
and treats the manual as Ravel-drawn if it is built at all.

## 15. Commands

One command tree rooted at the mod's own name, with seven subcommands (**read**):
read or write a runtime-changeable setting, report the entry's version, send a
diagnostic round-trip message and report the timing, set a target on fire, force
a resource reload on the client, dump the registries of §14, and open the
demonstration manual.

Five of the seven are the entry's own. The other two — the settings subcommand
and the version subcommand — are inherited from the framework, and every
dependent gets them without asking (**read**).

Permission levels are **unknown**; the read established the tree shape and did not
reach the permission predicates.

## 16. Host intrusion surface

The entry cannot do what it does without reaching into the host, and the reach is
declared rather than hidden, which makes it countable (**read**):

- **117 lines of access widening** over host classes, covering recipe lookup by

A counterpart running under Ravel needs the equivalent reach through Ravel's own
mechanisms, and this list is the shape of that requirement. It is not a
counterpart-implementable list on its own: several of these exist to let the

**unknown** and belongs to the counterpart's design rather than to this
specification.

The other host platform builds in the same repository patch nine more server-side
and four more client-side sites, but the pinned artifact is not built from them
and they are not this entry's behaviour (**read**).

## 17. What dependents need

RVL-132 is the wave's dependent and its plan row records it as depending on this
entry alone. What it consumes, counted from its declaring source (**inferred**,
and qualified below):

- **The capability-attachment registry**, by a wide margin the largest use. A
  dependent registers a constructor that attaches a capability to a block, a block
  entity, an entity or an item, addressed either by a specific registered type or
  by a supertype or entity category. The registry refuses registrations after it
  is baked, raising rather than ignoring them, and it installs its platform event
  listener lazily on first registration of each of the four target classes
  (**read**, from this entry's source). RVL-132's own product is a set of
  capabilities, so this is the mechanism it exists on top of.
- **The helpers**: block-entity lookup, item-store manipulation, fluid handling
  and side questions. The original hangs all four off a single accessor a
  dependent names first; that is the original's structure and the observable
  consequence is none, so do not port the shape.
- **The quantity collections of §10**, specifically the plain list, the linked
  list, the hash map and the filtered iterator.
- **The mod base and settings declaration of §5**, which is how it declares
  itself at all.
- **A single-use fluid tank** and **a mutable single-value box**, two small
  concrete utilities.
- **The parse error type of §11**, which it catches.
- **The game-test harness**, which is not in the shipped artifact's critical path
  but is in the dependent's build.

The four outside-wave dependents consume a strictly larger surface, since they are
where the widget toolkit, the manual engine, the storage moves and the difference
tracker are actually used. A counterpart that satisfies only §17's first list
satisfies RVL-132 and does not satisfy them.

**The qualification.** The consumption list above was counted from a checkout of
RVL-132's project at a **different revision** from the pinned artifact, because no
pinned source for RVL-132 was fetched for this specification. It is a reliable
guide to which subsystems matter and is not evidence about the pinned build's
exact surface. Whoever writes RVL-132's own specification should recount it
against the pinned revision and correct §17 if it differs.

## 18. What this specification does not specify

- **The widget toolkit, the render helpers and the manual page layout.** Ravel
  draws its own screens, and none of it describes behaviour a dependent observes
  from outside. §8 keeps only the menu and store semantics that survive.
- **The per-field encoder table of §6.** The read established that the table
  exists, where each half of it comes from and how it is keyed, and chose not to
  enumerate the portable entries. They are a plain list in the holder this
  specification already read, so a counterpart implementing the transport can
  enumerate them from there rather than re-deriving them.
- **The quantity-kind interface declarations of §10.** They were not in the
  fetched archive. The vocabulary above is inferred from sixty-seven use sites and
  the exact signatures are unknown. This is the single largest gap in this
  specification and it sits under the single largest body of behaviour.
- **Where the shared vocabulary of §10 lives on the Ravel side.** RVL-210 and
  RVL-132 share an interface package that ships inside RVL-210's artifact and that
  neither plan row names. Both counterparts need it and neither plan row owns it.
  That is a wave-level decision, not a specification claim, and it is raised here
  because it blocks both.
- **The search order of the shape detector (§12)**, the permission levels of the
  command tree (§15), and whether a runtime settings change is written back to
  its file (§5.3). Each is marked unknown where it occurs.
- **Save compatibility.** Seven registered identifiers are storable by a
  dependent or by a world. The names surface in the provenance record is
  unresolved, so no identifier mapping is specified and a save-compatible
  counterpart is not what this specification describes.
- **The cosmetic allow-list of §9 as written.** A counterpart is specified *not*
  to reproduce it. That is a deliberate divergence, stated in §9 with its reason.

**Coverage.** Read in full: the mod entry point, the settings framework's
declaration vocabulary and both of the entry's own settings, the full registration
census of §4, the wire-format ordering rule of §6, the value channel and its
seven readers (§7), the outbound fetch and both dormant network paths
(§9), the query grammar's complete handler list and its order (§11), the shape
detector's constraint vocabulary (§12), both persistence mechanisms (§13), the
command tree (§15), the full access-widening list and the patch set (§16), and
the build declarations, licence and changelog that pin the revision.

Read in part: the collection and storage semantics of §10, read across the
implementations and their tests but not against the absent interface declarations;
the menu and store behaviour of §8, read at the base types and not at every
subtype; the registry-dumping producers and the manual engine of §14, read at
their entry points only.

Not read: the widget toolkit and its layout, event and font handling; the render
and model helpers; the manual engine's page element types; the two non-pinned host
platforms' 113 files; and the 84 test files except where §10 needed them.

A reader who is also this specification's author has nothing contradicting them.
The markers above and this statement are what stands in for that contradiction.
They are weaker than a second reader and are not a substitute for one.
