# RVL-217 — behaviour specification

Wave: `waves/m6-foundation.json`. Method: source-informed reimplementation.
Rights: the upstream project and the separately published interface project it
ships alongside each carry an MIT licence file at their repository root; see
`provenance/m6-foundation.json` for pinned revisions and digests.

This document specifies **what the counterpart must do**. Confidence markers are
as in the other specifications in this directory: **read**, **inferred**,
**unknown**.

---

## 1. What this entry is

A cross-mod contract library. It publishes a small set of capability contracts
that any mod may implement and any mod may query, and it supplies
implementations of those contracts for stock game objects so that a querying mod
gets useful answers even when no other mod is installed (**read**).

It ships no blocks, no items, no recipes and no worldgen. It ships translations
for the names of the ingredient kinds it registers, and one small structure
resource whose purpose is test scaffolding (**read**). It has no creative tab
(**read**).

It runs on both sides. Nothing in its behaviour is client-only (**inferred** —
it constructs distinct client and common startup objects but nothing observable
differs; the reader did not find a client-only behaviour).

Two things it does are separable and should stay separable in the counterpart:

- **the contracts** (§2–§4) — what a querying mod can ask of an object;
- **the stock attachments** (§5) — the answers this entry supplies for objects
  the base game owns.

---

## 2. The capability contracts

Six capabilities are published. Each is addressable on a block (with a face),
on an item, and on an entity, so a caller can ask the same question of all three
(**read**). Whether the face is meaningful varies by capability and by
implementation, and the contracts do not require an implementation to distinguish
faces (**inferred**).

### 2.1 Work state

Answers two independent questions about a machine-like object:

- **has work** — is there a valid input present for it to process? For a stock
  smelting device this is true when the input slot holds something that device
  can smelt.
- **can work** — is it able to start, and not blocked by anything internal or
  external? For a stock smelting device this is true when it has fuel.

The contract stores nothing itself; the answers are computed from the object it
describes. When both answers are true, the object is expected to actually be
working (**read** — stated as an expectation in the source, not enforced).

### 2.2 Temperature

Reports a current temperature in kelvin, plus a maximum, a minimum, and a
default. The default is the value the object has in its freshly created state
(**read**). Zero degrees celsius is defined as 273.15 kelvin and every stock
implementation is expressed relative to it (**read**).

### 2.3 Inventory state

Reports a single integer summarising an inventory's current contents. The
contract's guarantees are asymmetric and must be reproduced exactly (**read**):

- if the contents change, the value **is guaranteed** to differ;
- a differing value does **not** guarantee the contents changed.

Callers gate expensive work on the value changing, so the first guarantee is
load-bearing and the second is explicitly not. The value must be cheap to
produce — precomputed if possible (**read**).

### 2.4 Slot-agnostic item store

A simplified item store where the provider, not the caller, is responsible for
choosing where things go. It offers (**read**):

- iteration over everything present;
- a search returning an iterator over everything matching a given stack under a
  set of match flags (see §3). The search must not modify the store, and its
  results must not be modified by the caller;
- insertion of a stack, returning what could not be inserted — empty if all of it
  was accepted. The input stack must not be modified;
- extraction of up to a given count, returning what came out, empty if nothing
  can be;
- extraction of something matching a given stack under match flags, returning
  what came out. **If the flags exclude the count, the given stack's count means
  "at most this many"** (**read**);
- a reported total capacity across the whole store.

Every mutating operation exists in a transactional form and in a simulate/commit
form, and the simulate form is defined as the transactional form run and rolled
back (**read**).

### 2.5 Recipe handler

Exposes what recipes a machine can perform and lets a caller simulate one
(**read**):

- the set of ingredient kinds it accepts as input and the set it produces as
  output;
- whether a given count of instances of a given ingredient kind is a valid input
  size for it;
- the recipes available through it, as definitions (§4). The collection SHOULD be
  exhaustive but is not required to be, and **no order may be assumed**;
- given a mixed set of input ingredients, the output that would be produced, or
  nothing if no recipe applies. Simulation must have no effect on the machine's
  state.

### 2.6 Aggregate ingredient storage

A capability that exposes, for a single object, one slot-agnostic store per
ingredient kind (§2.4 generalised beyond items). This is the capability callers
are told to use; the per-kind store is not itself a capability (**read**).

The per-kind store's contract adds two requirements beyond the item store's
(**read**):

- **Determinism.** Two consecutive simulated insertions of the same ingredient
  must return the same result, and a committed insertion must return what the
  simulation returned. A simulation *after* a commit may legitimately differ. The
  same holds for extraction.
- **Quantity semantics on extraction.** If the ingredient kind's primary
  quantifier is *not* part of the match condition, the prototype's quantity means
  "at most this many". If it *is* part of the match condition, the quantity means
  "exactly this many": the store must permit the extraction when it holds at
  least that much, and must refuse it when it holds less.

An implementation is free to store instances however it likes, including merging
equal instances and summing their quantities (**read**).

## 3. Matching

Matching is by flag set, and the flags are a public part of the contract because
callers compose them (**read**).

For items, four named flags exist: match nothing in particular, match the item
identity, match the attached data, match the count. A convenience value combines
the latter three. For fluids the same shape exists with fluid identity, attached
data, and amount.

Required semantics (**read**):

- The "match nothing in particular" set accepts every pair unconditionally.
- Two references to the same object match; two empty stacks match.
- An empty stack never matches a non-empty one.
- Otherwise every selected aspect must agree, and unselected aspects are ignored.

The numeric values behind the flags are a stored and transmitted format in the
original — they appear in saved recipe data and in cross-mod calls. **Whether the
counterpart must reproduce the same numeric values is unknown** and depends on
whether anything outside the counterpart's own tree will carry them. If nothing
does, the counterpart should express these as a proper set type rather than an
integer bitmask.

### 3.1 Attached-data comparison and its configuration

Comparing attached data has one configurable behaviour, and it changes results
across the whole game (**read**):

- A server-side setting lists data component types to **ignore** when testing
  equality. It defaults to empty.
- With the list empty, attached data is compared by plain equality.
- With the list non-empty, comparison ignores the listed types on both sides.
- Two sets of attached data that are both empty always compare equal without
  consulting the list.
- The setting is re-read on config load **and** on config reload, so a reload
  changes matching behaviour for subsequent calls (**read**).
- A second setting, off by default, enables diagnostic logging whenever two
  otherwise-equal items are found to have unequal attached data. Its comment
  warns it is expensive (**read**).

The ignore list is the reason this comparison is not simply structural equality,
and it is the piece a counterpart is most likely to get wrong by simplifying.

## 4. Ingredient kinds and recipe definitions

### 4.1 Ingredient kinds

An **ingredient kind** names a category of thing a recipe can consume or
produce. Each kind is registered under an identifier and carries a matcher, a
serialiser, a translation key, and a list of **category types** — the aspects of
an instance that can independently participate in matching (**read**).

Three kinds are registered by this entry (**read**):

- **items**, identified as `minecraft:itemstack`, with category types for item
  identity, count, and attached data. Item identity is marked as the kind's
  primary identifying aspect; count is marked as the kind's primary quantifier.
- **fluids**, identified as `minecraft:fluidstack`, with category types for fluid
  identity, amount, and attached data. Fluid identity is primary-identifying;
  amount is the primary quantifier.
- **energy**, identified as `minecraft:energy`, with a single category type for
  the amount, which is both primary-identifying and the primary quantifier.

Each kind's translation key follows the pattern
`recipecomponent.minecraft.<kind>` (**read**). The three identifiers and the
translation keys are stored and transmitted, and must be reproduced.

Registration order matters to nothing observable (**inferred**), but all three
kinds must exist before common setup completes: the original asserts their
presence there and fails startup loudly if any is missing (**read**). A
counterpart should keep that failure loud.

### 4.2 Storage adapters

After capabilities have been loaded, each kind is given adapters that turn a
foreign storage capability into a per-kind store (§2.6). Adapters are registered
for (**read**):

- energy, against the platform's energy capability on blocks, items and entities;
- items, against the platform's item capability on blocks, items and entities,
  and separately against this entry's own slot-agnostic item capability on all
  three;
- fluids, against the platform's fluid capability on blocks, items and entities.

The observable consequence is what matters: a caller asking a stock chest for an
item store gets one, without the chest knowing anything about this entry
(**read**). A counterpart that publishes the contracts but not the adapters would
pass a contract test and fail every real integration.

### 4.3 Recipe definitions

A recipe definition states, per ingredient kind (**read**):

- its **inputs**, as an ordered list of positions, where each position holds a
  set of alternatives that would satisfy it;
- for each input position, whether it is **reusable** — that is, whether a
  crafting job consumes it or can hand it back for later jobs;
- its **outputs**, as exact instances rather than alternatives;
- optionally, the identity of the built-in recipe it corresponds to.

Definitions are comparable and must implement equality and hashing consistently
(**read**).

### 4.4 The serialised form

Recipe definitions are written to and read from saved data, and the format is a
**required wire format** because saved worlds and cross-mod messages carry it.
Reproduce it exactly (**read**):

- If the definition names a built-in recipe, the serialised form is **only** that
  recipe's identifier, under the key `recipeId`, and nothing else is written. On
  read, the definition is rebuilt by looking that recipe up in the active level.
- Otherwise a list is written under `input`, one entry per ingredient kind, and
  **the kinds are written in sorted order** so the form is stable. Each entry
  carries the kind's registered identifier under `component`; a list of
  positions under `instances`; and an integer array under `reusable`, parallel to
  the positions, holding one for reusable and zero for not.
- Each position carries its alternatives under `val` and a single-byte
  discriminator under `type` naming which alternatives encoding was used. Two
  encodings exist: an explicit list of prototypes, and a reference to an item tag.
  A discriminator with no registered encoding is a read error naming the value.
- The outputs are written under `output` in the mixed-ingredients form.
- An unknown ingredient kind identifier on read is an error naming the identifier.

The sorting and the parallel arrays are the two things a reimplementation most
easily loses; both are observable through a saved world.

## 5. What is attached to stock game objects

This is the behaviour the wave's parity tests will actually exercise. Every item
below is **read** from the pinned source.

### 5.1 Work state

- The three stock smelting devices (the ordinary one and its two specialised
  variants) report **has work** when their input slot is non-empty, a recipe of
  that device's own kind matches that input, and assembling that recipe yields a
  non-empty result. They report **can work** when they are currently burning or
  when their fuel slot holds something with a non-zero burn duration.
- The stock brewing device reports **has work** when its current contents form a
  brewable arrangement, and **can work** when its fuel level is above zero.
- The stock open-fire cooking block reports **has work** when any of its slots is
  non-empty, and **can work** when its block state says it is lit.

### 5.2 Temperature

- The three stock smelting devices report `273.15 + their current total burn
  time`, a maximum of the largest representable double, and both a minimum and a
  default of 273.15. **This is not a physical temperature and the counterpart
  should not "fix" it into one**; callers compare these values across mods and a
  changed scale changes their behaviour.
- The stock open-fire cooking block reports 1373.15 when lit and 273.15 when not,
  with those two as its maximum and minimum/default.
- Any bucket-like item, including subtypes, reports the temperature its contained
  fluid declares, and 273.15 when it contains nothing. Its default is the fluid's
  own declared default, again 273.15 when empty.

### 5.3 Item stores

- Every colour of the stock portable container item, and the uncoloured one,
  expose their contents as an item store.
- The stock pocket container item exposes its contents as an item store.
- The dropped-item entity exposes the stack it carries as a one-slot item store,
  and likewise exposes a fluid store and an energy store delegating to whatever
  the carried stack itself offers.
- Both stock item-display entities do the same for the item they display.

The delegating behaviour is the notable part: querying a dropped item for a fluid
store answers with the fluid store of the item it is carrying, if that item has
one. A counterpart that returns nothing there changes observable behaviour for
every mod that pipes items around.

### 5.4 Recipe handlers

Recipe handlers are attached to (**read**):

- the stock brewing device, exposing its brewing recipes;
- the three stock smelting devices, each exposing its own recipe kind, accepting
  exactly one input, and treating the output as an exact single result;
- the stock crafting block, exposing shaped and shapeless crafting, accepting any
  input count above zero;
- the stock cutting block, exposing its recipe kind, accepting exactly one input;
- the stock smithing block, exposing its recipe kind, accepting exactly one input
  built from three specific slots.

Two per-handler behaviour switches appear across these registrations and both are
observable: whether the handler treats the recipe as producing a single exact
output, and whether it is permitted to produce more than one recipe result for
the same input (the cutting block is the only one where the latter is enabled).

### 5.5 One further integration

One optional integration exists for a specific third-party mod, activated only
when that mod is present, and several others are present in the source but
disabled (**read**). The disabled ones are not specified here and the counterpart
should not implement them. The active one is out of scope for this wave: it
depends on a mod that is not one of the five foundation entries, and specifying
it would require reading that mod's source, which this reader did not do and had
no rights finding for either way.

## 6. Startup obligations

In order (**read**):

- the alternatives encodings (§4.4) are registered before anything can serialise
  a recipe definition;
- the three ingredient kinds are registered into their registry;
- during common setup, the three kinds are asserted present, each kind is given
  the chance to gather capabilities, and the server is made to send the full
  list of recipe kinds to clients — which exists so that a client can rebuild a
  recipe definition from a recipe identity (**read**). A counterpart that omits
  this makes §4.4's `recipeId` form unreadable on the client;
- after capabilities are loaded, the storage adapters of §4.2 are registered.

All of this happens with low priority relative to other listeners of the same
events, so that mods registering their own kinds get to go first (**read**).

## 7. What this specification does not specify

- **The one active third-party integration** (§5.5), deliberately.
- **The disabled integrations** present in the source, deliberately.
- **The internal algorithm of any stock attachment.** §5 says what each answer
  is, in terms of the game state it is derived from. It does not say how the
  original reaches that state, and in at least one case the original reaches it
  by a means a Rust counterpart will not have (**inferred**). The answer is the
  contract; the route to it is not.
- **Whether the match flags' numeric values are part of the contract** (§3).
  Marked unknown, not guessed.
- **Threading and transaction nesting.** The store contracts are expressed in
  terms of a transaction context; this document does not specify that context's
  own semantics, isolation, or nesting rules. That is a platform contract Ravel
  must settle separately, and every store operation in §2.4 and §2.6 depends on
  it.
- **The test scaffolding resource** the entry ships. It exists; nothing here
  depends on it.
- **Coverage.** The reader read the whole published contract surface and the
  whole of the stock-attachment surface, and sampled the rest. The parts read in
  full are §2, §3, §4.1, §4.4 and §5. §4.2 and §6 were read from the registration
  sites only. Anything else in the entry was not read and is not specified.
