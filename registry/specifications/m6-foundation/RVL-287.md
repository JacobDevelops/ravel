# RVL-287 — behaviour specification

Wave: `waves/m6-foundation.json`. Method: source-informed reimplementation.
Rights: the upstream project's repository root carries an MIT licence file, read
at the source; see `provenance/m6-foundation/RVL-287.json` for the pinned
revision, the licence identity and the digest.

Confidence markers: **read**, **inferred**, **unknown**.

This entry is a foundation seed: the wave admits it with no dependency of its
own, and three pack entries depend on it (**read**, from the wave manifest, the
plan row and the graph). It is a rendering library, not a mod: it declares no
block, no item, no recipe, no tag, no loot and no world data, and a player never
encounters it directly. What its dependents observe is one facility — a way to
say, in a block's own state-to-model document, "draw this block with a
neighbour-aware model of kind K" and have a model built for every position the
block occupies. Sections 4 to 11 are that facility and are the load-bearing part
of this document.

---

## 1. What this entry is

A client-side rendering library with no gameplay of its own. The pinned tree
holds sixty files, thirty-eight of them source (**read**, counted over the whole
tree twice). Those thirty-eight split into twenty-two in a portable module,
ten in the loader module the pinned artifact is built from, and six in a second
loader module the pinned artifact does not contain (**read**). Only the first
two are in scope; the third is named here so a later reader does not count it.

The tree carries four declaration documents — two mixin configurations and two
mod descriptors — and no game asset at all: no texture, no sound, no model
document, no image source (**read**, counted twice). It does carry one binary,
the build wrapper's own jar, which is build tooling and not content.

It declares the loader and the game as its only two dependencies and depends on
no other pack entry (**read**, from the mod descriptor, confirmed against the
plan row's count of two platform dependencies).

### 1.1 Ravel disposition

Ravel already owns resource-pack reload, side isolation and content
declaration, and a counterpart expresses those through Ravel rather than
rebuilding them. What survives as genuine counterpart work is the portable
decision logic: the quadrant selection rule of §6, the connection condition
language of §7, the neighbourhood probe of §8, the per-kind geometry of §9 and
the texture slot arithmetic of §10.

The bake-time and atlas-facing halves are host-blocked at the reviewed public
revision rather than declined: Ravel publishes no model-baking surface. They are
named where they occur. Nothing here is declined outright.

## 2. Side, lifecycle and what a dedicated server never loads

**This entry does nothing whatsoever on a dedicated server** (**read**). Its
whole construction body is guarded by a test for a client distribution; on a
server the constructor runs, takes the guarded branch, and returns having
registered nothing. Both mixin configurations list their targets under the
client-only key, so on a server no bytecode is transformed either.

The client lifecycle, in order (**read**):

1. At construction, on a client only, the eight built-in model kinds of §5 are
   registered into a process-wide table keyed by kind identifier. Registering a
   kind identifier twice is refused with an error rather than silently
   overwriting. Keep the refusal.
2. Still at construction, on a client only, two loader listeners are added: one
   that publishes this entry's model loader to the loader's geometry registry
   under a fixed identifier, and one that registers the reload listener of §4.
3. On every resource reload, the listener of §4 rebuilds its table of
   declaration documents from the reloaded packs.
4. During model bakery construction, an injected hook hands the reload listener
   a reader over the game's own already-parsed state-to-model documents (§4.2).
5. During baking, each candidate model identifier is offered to every registered
   kind in turn; the first kind that claims it substitutes its own model (§4.3).
6. At chunk build time, each block position is probed once for all six faces and
   the resulting quad lists are attached to that position's model data; at quad
   collection time those precomputed lists are turned into baked quads (§11).

**Consequence for the side matrix.** Two of the three inbound edges are declared
client-only and match this behaviour. The third is declared required on both
sides (§3). A counterpart must therefore still *load and resolve* on a dedicated
server while contributing nothing there. Loading and doing nothing is the
correct server behaviour, not a gap.

## 4. How a model declaration is found

### 4.1 The two lookup paths

A declaration is a JSON object carrying a key whose value names the model kind
(**read**). Two paths reach one (**read**, in this order):

1. A dedicated reload directory. The reload listener collects every JSON
   document under one fixed top-level directory name across all loaded resource
   packs, keyed by the identifier the file path yields.
2. Failing that, the game's own state-to-model documents. The requested model
   identifier is rewritten into the path of the corresponding state-to-model
   file and handed to the reader of §4.2; every candidate document at that path
   is checked in pack order and the first one carrying a matching kind value
   wins.

In both paths a document is accepted only if the kind key is present *and* its
value equals the kind being asked about (**read**). What a mismatch does differs
between the two paths, and the difference is load-bearing (**read**):

- **Path 1 short-circuits.** If the dedicated directory holds a document under
  the requested identifier at all, that document is checked once and its verdict
  is final. A missing or differing kind value ends the lookup with no result;
  path 2 is never tried for that identifier.
- **Only path 2 iterates.** It walks every candidate document at the rewritten
  path in pack order and takes the first one whose kind value matches, skipping
  the rest.

A counterpart that treats path 1 as a fallible first attempt and falls through
to path 2 resolves declarations the original leaves unresolved.

**The directory name and the kind key spelling are compatibility-required.** A
pack author writes them by hand, so a counterpart that renames either cannot
load an existing pack's documents. Both exact spellings are obtainable from the
pinned artifact and are deliberately not transcribed here.

### 4.2 The reader over the game's own documents

The listener holds a function from a resource path to a list of already-parsed
documents, defaulting to one that returns nothing. That function is installed by
an injected hook during model bakery construction, from the map the bakery has
just built (**read**). Before that hook runs, path 2 of §4.1 yields nothing.

**Host-blocked.** Reaching inside the game's model bakery to borrow its parsed
documents needs a surface Ravel does not publish. A counterpart implements
path 1 unconditionally and records path 2 as blocked.

### 4.3 Substitution at bake time

An injected hook wraps the bakery's per-model bake call. For the model
identifier being baked, every registered kind is asked in turn whether it has a
declaration for it; the first that answers substitutes its own unbaked model for
the one the bakery was about to bake, and baking proceeds normally (**read**).

Two rules fall out (**read**):

- Iteration order over the kind table decides ties. The table is an unordered
  hash map, so **when two kinds both claim an identifier the winner is
  unspecified**. See §12.
- A model identifier whose variant is the inventory variant is refused before
  any lookup, so item models are never substituted.

**Host-blocked** for the same reason as §4.2.

## 5. The model kinds

Eight kind identifiers are registered, backed by seven distinct behaviours: two
of the eight names share one behaviour (**read**, counted twice). Named for what
they do:

| Kind | Behaviour |
| --- | --- |
| connected block | §9.1 quadrant connection on a full cube |
| connected carpet | §9.2 quadrant connection on a thin horizontal slab |
| connected pane | §9.3 quadrant connection on a pane, driven by state flags |
| large tiled block (two names) | §9.4 a texture grid tiled across world coordinates |
| rotating column | §9.5 axis-aware continuation, rotated per face, appearance-identity test |
| upright column | §9.6 as §9.5, block-identity test, never rotated |
| pane column | §9.7 column continuation on a pane |

A counterpart registers all eight names. Dropping the duplicate name breaks any
pack that spells it.

## 6. The quadrant selection rule

Every connection-based kind reduces three booleans to one of five texture slots
(**read**). Given whether the first neighbour connects, whether the second
connects, and whether their shared diagonal connects:

| first | second | diagonal | slot |
| --- | --- | --- | --- |
| yes | yes | yes | fully surrounded |
| yes | yes | no | inner corner |
| yes | no | — | first-axis edge |
| no | yes | — | second-axis edge |
| no | no | — | isolated |

All eight input combinations are covered and the diagonal is consulted only when
both neighbours connect. This is the single most parity-testable rule in the
entry: a counterpart's table must agree on all eight rows.

The five slots are also the five named entries a pack author writes in the
texture object of a connection-based declaration. Those five key spellings are
compatibility-required and obtainable from the pinned artifact.

## 7. The connection condition language

A declaration may carry a condition object describing which neighbouring block
states count as connected. Absent the condition key entirely, the default is
**exact state identity** — the neighbour connects only if its state is the very
same state object (**read**). If the key is present but its value is not an
object, the result is **never connects** (**read**).

Inside the object, a type discriminator selects one of eight forms (**read**;
the discriminator's own spelling and the eight type words are
compatibility-required and obtainable from the pinned artifact):

| Form | Behaviour | Degenerate input |
| --- | --- | --- |
| same state | neighbour state is identical to self's | — |
| same block | self's state is of the neighbour's block | — |
| named block | neighbour is that block, optionally with named state properties matching | unknown or unparseable block name → never; a properties value that is not an object → never; an unknown property name or a non-string value → that constraint is silently dropped |
| named tag | neighbour is in that block tag | a missing or unparseable tag name **raises** instead of returning never, unlike every sibling form. See §12 |
| negation | inverts a nested condition | a non-object body → never |
| conjunction | all of a list | empty list → never; single element → that element |
| disjunction | any of a list | empty list → never; single element → that element |
| exclusive-or | the two disagree | any arity other than exactly two → never |
| *any other or absent type* | never | — |

Non-object elements inside a condition list are silently skipped before the
arity rules above are applied, so a two-element list holding one non-object is
an empty-or-single list, not a two-element one (**read**). That interaction is
easy to miss and a parity test should cover it.

The named-block form's property matching compares property values by reference
identity against the values parsed out of the declaration (**read**). For the
game's own property value types this is sound because those values are interned;
a counterpart compares by value, which is the same answer by a safer route.

Note the asymmetry a counterpart must preserve: the *default* condition (no key)
is state identity, while an *unparseable* condition is never-connects. Silently
falling back to the default on a malformed document would connect blocks a pack
author asked not to connect (**read**).

## 8. The neighbourhood probe

For a given block face, eight neighbours are sampled: the four in-plane
orthogonals and the four in-plane diagonals, each expressed relative to the face
being drawn rather than to world axes (**read**). The mapping from face plus
in-plane direction to a world offset is a fixed six-by-four table; it is
arbitrary but must be reproduced exactly, because it decides which way a
connected texture runs on each face.

Each sample resolves through the game's *appearance* query rather than the raw
block state, so a neighbour that presents itself as another block for rendering
purposes connects as that other block (**read**). Two guards apply (**read**):

- A sample whose appearance is air never connects, checked before the condition
  of §7 runs.
- Before any of this, if the block directly in front of the face presents an
  appearance of the same block and is not air, the face is culled entirely and
  no quads are produced.

The condition of §7 is applied to the *appearance* of self as seen from the
sampled position, against the *appearance* of the sample — not to the two raw
states. A counterpart that compares raw states will connect correctly in the
common case and diverge exactly where a dependent uses appearance overrides.

**Host-blocked**: the appearance query and the culling test both need live block
state access from the render thread, which Ravel does not publish.

## 9. Per-kind geometry

Every kind returns a list of quads for one face. A quad is a texture slot, four
edge positions in unit face coordinates, a rotation, an inset depth, and whether
it is cullable (**read**). Cullability defaults to "cullable exactly when the
inset depth is zero", which is what makes a flush quad participate in the game's
face culling and an inset quad not (**read**).

### 9.1 Connected block

If the face is occluded per §8, no quads. If all eight neighbours connect, one
full-face quad in the fully-surrounded slot. Otherwise four half-by-half quads,
one per face quadrant, each selected by §6 from its own two orthogonals and
their shared diagonal (**read**).

### 9.2 Connected carpet

Horizontal faces return one fixed thin edge quad. Vertical faces run the
quadrant logic of §9.1 with two differences (**read**). This kind performs no
occlusion cull at all, so a face is never dropped for what sits in front of it.
And every quad carries an inset depth that differs between the top face and the
bottom face, placing the sheet one-sixteenth of a block from the respective
surface. The all-eight-connected case is present as in §9.1 and returns one
full-face quad, but from a different slot for the top face than for the bottom.

### 9.3 Connected pane

Connection here does **not** use the condition language of §7. A neighbour
connects only if it is the same block *and* both of its two in-plane
perpendicular state flags are set — that is, the neighbouring pane runs across
this face rather than into it (**read**).

Vertical faces are culled outright when the block in front is the identical
state; otherwise they return a cap: a fixed centre quad plus one arm quad per
set directional state flag, with the two depth-axis flags swapped when the face
points down. On a horizontal face, all eight neighbours connecting returns one
full-face centre quad before any in-plane flag is consulted. Otherwise the face
branches on the two in-plane flags: both set gives
four quadrant quads whose inner edge shifts by a sixteenth depending on the
face's own flag; exactly one set gives a single quad occupying the corresponding
side; neither set, with the block in front differing and this face's flag clear,
gives one narrow middle strip; otherwise nothing (**read**).

### 9.4 Large tiled block

A width and a height are declared, and a texture is declared for every cell.
For a face, two of the position's three absolute world coordinates are chosen by
the face's axis, one of them mirrored for three of the six faces, and the pair
is reduced modulo the grid to a cell index (**read**).

**The index arithmetic is defective in two independent ways** (**read**). The
row stride multiplies by the grid *height* where it must multiply by the
*width*, so any grid whose width and height differ addresses the wrong cells
and, past the last row, slots that were never declared. Separately, on the two
faces whose axis is vertical the mirroring offset is derived from the grid
*width* while the coordinate it mirrors is the one reduced modulo the grid
*height*, so those two faces address wrong cells on a non-square grid even once
the stride is corrected. Both are right only for square grids. See §12.

Because this kind keys off absolute world coordinates and never consults a
neighbour, its output depends on where the block sits, not on what is beside it.

### 9.5 Rotating column

The face's occluding neighbour is queried for an axis property. If it has none,
one standalone-slot quad. If its axis equals the face's axis, one cap quad.
Otherwise the two neighbours along that axis are tested for mutual appearance
identity, and the pair of results selects among four slots: both give the
continuation slot, one gives the corresponding end slot, neither gives the
standalone slot. Every non-cap quad carries a rotation derived from the axis and
the face, from a fixed table (**read**).

**Two defects here.** The axis property is read from the *neighbour's*
appearance rather than the block's own, so the column's rendering is decided by
what sits in front of each face. And the mutual-identity test compares state
objects by reference rather than by block, unlike every sibling kind. See §12.

### 9.6 Upright column

Same shape as §9.5 with three differences (**read**): occlusion culls the face
outright; vertical faces always return the cap slot without consulting an axis
property; and the two vertical neighbours are compared by *block*, not by state
reference. No rotation is applied to any quad.

### 9.7 Pane column

The pane geometry of §9.3 with the slot selection of §9.5: the quads and
the in-plane flag branching come from the pane kind, while the slot index comes
from testing the block above and below for same-block identity with both
perpendicular flags set. Vertical faces return the same cap as §9.3 (**read**).

## 10. Texture slots and index assignment

Two slot schemes exist (**read**):

- **Flat.** Most kinds hold one map from slot number to texture and hand it
  straight to the atlas, so a declaration's slot numbers are the runtime indices.
  The pane kinds add two further slots for their two edge textures, each
  defaulting to the particle texture when not declared.
- **Per-face.** The connected block kind holds a separate texture set per face
  and assigns runtime indices by walking the six faces in the game's own face
  order, allocating a fresh sequential index per entry, and recording a per-face
  map from slot number to that index. A face with no texture set gets an empty
  map and every lookup against it falls back to index zero (**read**).

The per-face assignment has two consequences a counterpart must keep: identical
textures across faces are deduplicated by texture identity before indices are
handed out, so one atlas sprite may back several indices; and the sequential
numbering means indices are meaningful only through the per-face map, never
directly.

A connected block declaration is accepted in three shapes through *two* parse
attempts, tried in order (**read**). The first attempt reads a single five-entry
texture object and applies it to all six faces. The second attempt covers the
remaining two shapes together: it walks the six faces, taking a face that is a
single texture string as that texture and any other face as a five-entry object,
falling back to a shared default object for a face that declares none. If
neither attempt parses, the declaration is rejected with a syntax error. The
parse-attempt helper swallows every exception, so a malformed first attempt
falls through to the second rather than failing (**read**).

Slot zero is the particle texture throughout, and a model whose texture set has
no slot zero falls back to the game's missing-texture sprite (**read**).

## 11. Precomputation, baking and culling

Per block position, all six faces are probed once and the results split into
cullable and non-cullable quads. The cullable quads are stored under their own
face; all non-cullable quads across all six faces are stored together under a
null face key. At quad-collection time, a request for a specific face yields
that face's cullable quads and a request for no face yields the pooled
non-cullable ones (**read**).

Each stored quad is turned into a box element one quad thick, positioned by a
fixed per-face coordinate transform, with the face's texture coordinates derived
from that box and a rotation applied in ninety-degree steps, then handed to the
loader's element baker (**read**). The transform tables are arbitrary but
must be reproduced exactly; they are the difference between a correct texture
and a mirrored one.

Ambient occlusion is on, block light is used, and the render type is whatever
the declaration named, from a fixed four-name vocabulary, or the game's default
when unnamed (**read**). Those four names are compatibility-required and
obtainable from the pinned artifact.

Quad collection wraps its body in a catch that logs and rethrows, because the
game swallows the exception otherwise (**read**). The intent is sound; a
counterpart surfaces the error through Ravel's own diagnostics instead.

**Host-blocked**: the whole of §11 needs a model-baking surface Ravel does not
publish.

## 12. Defects a counterpart must fix rather than reproduce

Seven defects were found by reading. None is compensated for elsewhere in the
tree; each is a straightforward mistake (**read**, except where marked).

| # | Where | What is wrong | What a counterpart does |
| --- | --- | --- | --- |
| 1 | §9.4 large tiled block | The row stride uses the grid height where it needs the width, so non-square grids address wrong or undeclared cells | Multiply the row by the width |
| 2 | §9.4 large tiled block | On the two vertical-axis faces the mirroring offset comes from the grid width while the coordinate it mirrors is reduced modulo the grid height, so those faces are wrong on a non-square grid independently of defect 1 | Mirror by the same extent the coordinate is reduced by |
| 3 | §9.5 rotating column | The axis property is read from the occluding neighbour's appearance instead of the block's own state | Read the block's own axis |
| 4 | §9.5 rotating column | Continuation is tested by state reference equality while every sibling kind tests block identity, so two states of one column block do not continue into each other | Test block identity, as §9.6 does |
| 5 | §7 named-tag condition | A missing or unparseable tag name raises out of declaration parsing rather than returning never-connects, and nothing on that path catches it, so one malformed declaration fails the whole model | Return never-connects, as every sibling form does |
| 6 | §4.3 bake-time substitution | The kind table is an unordered map, so which kind claims a contested identifier is unspecified by contract; it is stable for a given set of registered kinds but may change with any version that alters the key type's hashing or the table's capacity (**inferred**: hash map iteration order is unspecified, and the key's hash is content-derived) | Iterate a deterministic order and record it |
| 7 | The nullable-keyed face map | Its key-set and entry-set views index one past the value array and one before the key array, so both throw rather than returning a view | Use a container whose views work, or do not expose them |

Defect 7 is latent in the pinned tree because nothing calls those two views
(**read**). It is listed because a counterpart that ports the container
faithfully would inherit a broken one.

Defects 1 to 4 are visible to a player and defect 5 is a hard load failure. A
parity test against the original will *disagree* with a corrected counterpart on
exactly these five, so the test must encode the corrected behaviour and cite
this section, not the original's output.

## 13. What a counterpart implements

In Ravel terms, and in dependency order:

1. **The quadrant rule (§6)** as a pure function of three booleans. Eight rows,
   fully testable, no host surface.
2. **The condition language (§7)** as a parsed predicate tree over a block-state
   abstraction, including every degenerate-input row of the table and the
   correction of defect 5.
3. **The neighbourhood probe (§8)** as a pure function of a face and a neighbour
   accessor, with the six-by-four offset table reproduced exactly.
4. **The seven geometries (§9)** as pure functions from probe results and state
   flags to quad lists, with defects 1 to 4 fixed.
5. **The slot assignment (§10)** including the three declaration shapes and the
   per-face sequential numbering.
6. **The declaration lookup (§4.1 path 1)** through Ravel's resource-pack reload.
7. **Everything else** — path 2, bake-time substitution, the appearance query,
   and all of §11 — recorded as host-blocked pending a Ravel model surface.

Steps 1 to 5 are the whole of the counterpart's testable behaviour and none of
them needs a running game.

## 14. Compatibility-required spellings

Five spellings must match the original exactly or existing packs stop loading.
Each is named here for what it does; every exact spelling is obtainable from the
pinned artifact and none is transcribed. The descriptive names this document
gives the eight kinds in §5 and §9 are chosen for behaviour, not derived from
the identifiers, and two of them use a noun — carpet, pane — that is both an
ordinary English word and a vanilla block name and that also appears as a
segment of the corresponding identifier. That coincidence is descriptive rather
than a transcription, but a reader checking clean-room hygiene should know it is
there. The five spellings are:

1. The reload directory name that declaration documents are collected from.
2. The declaration key whose value names the model kind.
3. The eight model kind identifiers of §5, including the duplicate pair.
4. The condition type discriminator and its eight type words (§7), plus the
   named-block and named-tag key names.
5. The texture slot names in a declaration's texture object (§6, §9.3, §10) and
   the four render-type names of §11.

`provenance/m6-foundation/RVL-287.json` records the names surface as unresolved
for exactly this reason: pack compatibility requires spellings the licence does
not clear.

## 15. What this specification does not specify

- **How quads reach the screen.** Vertex formats, atlas stitching, chunk mesh
  assembly and the loader's element baker are the host's, described here only as
  far as §11 needs.
- **The second loader module.** Six source files for a loader the pinned
  artifact does not contain were not read and nothing here describes them.
- **The exact coordinate transform tables** of §8 and §11. Their shape and their
  load-bearing role are stated; the numbers are obtainable from the pinned
  artifact and a counterpart must derive them there rather than from prose.
- **What the three dependents actually call.** §3 reasons from the graph edges
  alone; no dependent's source was read (**inferred**).
- **Any server behaviour**, because there is none (§2).
- **Whether defects 1 to 4 are relied on by a dependent's shipped resource
  packs** (**unknown**). If RVL-130 ships a non-square tiled grid tuned around
  defects 1 and 2, correcting them changes that mod's appearance. Nothing in
  this tree answers that and no dependent pack was opened.

**Coverage.** Every one of the thirty-two in-scope source files was read in
full, twice for the counted claims. Read completely and specified above: the
quadrant rule, the condition language, the neighbourhood probe, all seven
geometries, both slot schemes, the declaration lookup, the lifecycle and the
side split. Read completely but specified only in outline because they are host
concerns: the bake path of §11 and the two injected hooks of §4.
